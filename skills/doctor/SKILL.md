# /devflow:doctor

Arguments: $ARGUMENTS

Reports the health of the devflow setup. Read-only by default. With `--fix`, change only what the user confirms (AskUserQuestion): one item at a time, except the single confirmation of the merged-branch list in check 5. Never merge, never force push, never push to the base branch or a protected branch, never delete a protected branch or the base. GitHub operations go through the GitHub MCP server (load its tools with ToolSearch). No `Co-Authored-By` or AI attribution anywhere.

**Merged state:** never trust a `merged` field from a PR list or search result; the GitHub MCP list tools report `merged: false` for merged PRs. A PR is merged when `pull_request_read` (method `get`) returns a non-null `merged_at`, or when `git merge-base --is-ancestor <head sha> <remote>/<baseBranch>` succeeds after a fetch. Closed with neither: closed without merging. Take "merged by" and "merged at" from `pull_request_read`, not from a list.

Run all checks even when one fails. If `.claude/devflow.json` is missing, report fail for check 1, suggest `/devflow:init`, and run only checks 3, 8, 9 and 10 (none of them needs the config).

## Checks

1. **Config.** `.claude/devflow.json` parses and validates against `.claude/devflow.schema.json` (required keys, types, no unknown keys). Compare `devflowVersion` with the installed plugin version (`version` in `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`). A lower major or minor version, or a missing value: warn, suggest `/devflow:init --upgrade`. A lower patch version only is ok: patch releases never change templates, the schema or config keys. Also warn when `mergeGate.enabled` is true and the effective required list is empty, whatever `review.github` is (the effective list is `mergeGate.requiredChecks` without `devflow/review` while `review.github` is off, as is when it is on): the merge gate will refuse to merge; list the `name:` of each workflow in `.github/workflows/` as candidates for CI checks to add to `requiredChecks`.
2. **Templates.** Compare byte for byte every installed template file with the plugin's (the same list and comparison as `/devflow:init --upgrade`: the three workflows, `.github/scripts/devflow-merge-gate.cjs`, `.claude/devflow.schema.json`; a reusable-mode caller is compared with `templates/github/callers/` and its pinned tag with the plugin version). List the drifted ones. Report only; the fix is `/devflow:init --upgrade`.
3. **GitHub access.** Probe each connected GitHub MCP server for the authenticated user (`get_me`), as `/devflow:init` does; `fail` when none answers. Report the tool prefix of the server it used (for example `mcp__github__*`): the allowed GitHub MCP prefix whose server answered, or, when no allowed prefix answered, the server doctor used. Then check `.claude/settings.json`: it is `warn` only when it allows another GitHub MCP prefix and no allowed prefix belongs to a server that answers (background sessions would be refused); `ok` when an allowed prefix belongs to a server that answers, for example when both are allowed or the user picked one of several servers in init; when no GitHub MCP prefix is allowed at all, leave it to check 8. Check whether `gh` is installed (`gh --version`). Missing `gh` is only a warn; say that when `gh` is missing and the MCP connection drops, runs stop.
4. **Worktrees.** `git worktree list`, restricted to `worktree.dir`. For each: clean or dirty, branch, pushed or not (`git status --porcelain`, branch against `<remote>/<branch>`). `--fix`: remove (`git worktree remove`, no `--force`) the clean ones whose branch is pushed, after a yes per item; never a dirty one. A worktree whose branch belongs to a merged devflow PR is left to check 5, so it is not offered twice.
5. **Branches.** `<remote>` is `github.remote` (default `origin`). Run `git fetch <remote> --prune` first.
   - **Merged devflow PRs.** For every PR labelled `labels.devflow` with a non-null `merged_at` (Merged state rule), list its leftover remote head branch (`<remote>/<branch>`), local branch and worktree. Without `--fix` only list them.
   - **`--fix` for merged PRs.** Ask ONE AskUserQuestion for the whole list. After a yes, re-check each item right before deleting it, and skip it with the reason when a re-check fails: `merged_at` is still set; no open PR has the branch as base or head; the branch is not `baseBranch`, not in `protectedBranches` and not the current branch; a worktree is not the directory doctor runs in (the current directory). Then delete: the worktree with `git worktree remove <path>` (never `--force`; a dirty worktree is kept and reported), the local branch with `git branch -d <branch>` only (when it refuses, print `git branch -D <branch>` for the user to run: the guard hook blocks `-D` for Claude), the remote branch with `git push <remote> --delete <branch>`. Remove the worktree before its local branch. A remote branch that is already gone is not an error.
   - **Closed without merging.** Local and remote branches matching `branchPattern` whose PR was closed with no `merged_at` and no merge into the base are listed too, but `--fix` asks a separate per-branch yes for each (the single confirmation does not cover them), then deletes with the same commands. Its re-checks differ only in the first item: the PR is still closed and `merged_at` is still null (not reopened, not merged), instead of "`merged_at` is still set"; the shared re-checks (no open PR has the branch as base or head; not `baseBranch`, `protectedBranches` or the current branch; the worktree is not the current directory) still apply. Never the base, never `protectedBranches`, never a branch with an open PR.
   - **Automatically delete head branches.** Read the repository setting with `gh api repos/<owner>/<repo> --jq .delete_branch_on_merge` (`github.owner`, `github.repo`): `ok` when `true`; `warn` when `false` (turn on Settings > General > "Automatically delete head branches" so GitHub removes the branch on merge); `unknown` when it cannot be read (`gh` missing, no access). Report only; never change the setting.
6. **Idle in-progress issues.** Report open issues labelled `labels.inProgress` with no running session (`claude agents`), no open PR and a claim older than 2 hours. With `--fix`, after a yes per issue, re-check those conditions, delete the idle run’s claim comment and swap `labels.inProgress` for `labels.ready`. Remove the assignee only when it is the authenticated user and keep other assignees.
7. **Open PRs.** Open PRs labelled `labels.devflow` that are behind their base, conflicting, or have red checks. Report them and point at `/devflow:sync #<pr>`. Never fix them here.
8. **Allow-list.** `.claude/settings.json` has the `permissions` allow rules background sessions need: the output of `node "${CLAUDE_PLUGIN_ROOT}/bin/devflow-setup" allow < .claude/devflow.json` (git, the remote, checks, verify, worktree setup, MCP tools; use the GitHub MCP prefix the project already allows). List what is missing (warn), and the `manual` commands the user must allow by hand (no safe specific prefix). A bare interpreter, shell or runner rule already in the list (`Bash(python3:*)`, `Bash(node:*)`, `Bash(bash:*)`, `Bash(npx:*)`) is a warn: it allows any code; suggest the specific rule instead. `--fix` after a yes: merge them in; never add a deny rule or a rule that allows merging a PR or pushing to a protected branch.
9. **Owned by the plugin now.** Project files and rules that duplicate what the plugin does: `.claude/hooks/block_git_add_all.py` and its test, the `settings.json` hook that runs it and a `hook-test` style entry in `checks`; deny rules the guard enforces (force push, `gh pr merge`, pushes to protected branches, destructive git, `git add -A`); a maintenance `.claude/loop.md`; a project `.claude/agents/code-reviewer.md`. Build the list with `node "${CLAUDE_PLUGIN_ROOT}/bin/devflow-setup" leftovers` given `{"settings": <.claude/settings.json>, "config": <.claude/devflow.json>, "files": <git ls-files .claude>}`. Report each as `warn` with why it is removable and what replaces it. Never delete, edit or unregister any of them, also not with `--fix`: the user removes them (a project agent may hold project rules worth moving into CLAUDE.md first; say so).
10. **Guard.** The guard hook must work on this machine, or nothing blocks merges, force pushes or `git add -A`. Run `printf '%s' '{"tool_name":"mcp__x__merge_pull_request","tool_input":{}}' | python3 "${CLAUDE_PLUGIN_ROOT}/hooks/guard.py"; echo $?` and expect exit status `2`. Anything else (python3 missing, a crash, exit 0) is `fail`: the guard is not protecting this machine. Fix: install Python 3.9+ and make sure `python3` is on the PATH of non-interactive shells (the hook runs without your shell profile); if it still crashes, report the guard's stderr to the plugin maintainers. Read-only; `--fix` has nothing to change here.
11. **Release tag.** The declared version must have its tag. The declared version is `version` in `.claude-plugin/plugin.json` when that file exists, else the newest changelog version heading (the first `## [X.Y.Z]` heading of `CHANGELOG.md`, semver only; `[Unreleased]` and non-semver headings are ignored). When both exist and differ, report `warn` (name both versions). Then check that the tag `<release.tagPrefix><version>` (`release.tagPrefix`, default `v`) exists: `git fetch <remote> --tags`, then `git tag -l <tag>` or the GitHub MCP tag tools; `warn` naming the missing tag when it does not. `ok` otherwise. Skipped (no row) when the project has neither a `plugin.json` version nor a changelog version heading. Read-only; `--fix` has nothing to change here (a tag is created by the GitHub release, never from the shell).
12. **Stale follow-ups.** Open issues labelled `labels.triage` that Ship filed as follow-ups (title starts with `[follow-up #`) may already be fixed by a later change. For each, read the body: a `Found in: #<pr>` line and a `file:line` record. With a `file:line` record, run `git log -L` on the base (`git log -L <line>,<line>:<file> <remote>/<baseBranch>` after `git fetch <remote> <baseBranch>`) for that `file:line` and look for a commit dated after the issue was created; one is a hit, and a deleted file counts as changed (the file no longer exists on the base, or the log shows its deletion). Without a `file:line` record, search merged PRs (Merged state rule) for one that mentions `#<n>` (the follow-up's number) in its title or body: a hit makes it stale. Report each hit as `warn` listing the issue, the commit or PR that changed it, and the text "may be fixed, check and close". Doctor never closes an issue, never edits or relabels it and never comments on it, also with `--fix`: a human checks and closes it. No hit, or no such issue: `ok`. A `git log -L` that cannot run (line out of range on the base, no git history) is `unknown` for that issue, never a hit. Read-only.
13. **Closed issues with state labels.** List closed issues in the configured repository carrying any of `labels.inProgress`, `labels.review` or `labels.blocked`, with the labels found on each. Skip pull requests. With `--fix`, after a yes per issue, confirm it is still closed and remove only the listed state labels that are still present.
14. **Stale claims.** List open issues in the configured repository with a `devflow-claim` comment, no `labels.inProgress` label and no open PR linked to the issue. With `--fix`, after a yes per issue, re-check those conditions and delete only the listed claim comments. Never delete claim comments from in-progress issues.

## Report

Print a table: check, status (`ok` / `warn` / `fail`; the head-branch setting line may be `unknown`), what to do. `fail` is something that stops the workflows (config invalid, MCP unreachable); `warn` is drift or leftovers. With `--fix`, add a line per fix applied or declined. End with the one command to run next, if any.

## Waiting on you

After the report, print a "Waiting on you" section: what needs a human or a command now, one line per item with one command. It is read-only: it never changes anything, also with `--fix` (no label, comment, branch or file is touched, and nothing here is offered as a fix). It needs `.claude/devflow.json` for the labels; without it, print one line saying so and skip it. Use the GitHub MCP server and the Merged state rule.

Categories, in this order. Each issue or PR appears once, in the first matching category (blocked, PR waiting for a merge, conflict or behind, ready, sub-issue not ready, epic to accept):

1. **Blocked.** Open issues labelled `labels.blocked` with an open question: `/devflow:answer #n`.
2. **PR waiting for a merge.** Open PRs labelled `labels.devflow` that are mergeable, not behind and not draft, with green checks, which a human merges (`risk:high`, or the merge gate is off or does not take it): merge it yourself. Claude never merges.
3. **PR in conflict or behind.** Open PRs labelled `labels.devflow` that conflict or are behind their base: `/devflow:sync #pr`.
4. **Ready.** Open issues labelled `labels.ready` with no open PR: `/devflow:next-task` or `/devflow:dispatch`.
5. **Sub-issue not ready.** Open sub-issues of an open epic (label `type:epic`) that do not carry `labels.ready` (and are not blocked, in progress, labelled `labels.review` or already with an open PR): label it `labels.ready` once triaged, by hand.
6. **Epic to accept.** Open epics whose sub-issues are all merged (Merged state rule) and that have no `<!-- devflow-accept -->` result comment: `/devflow:accept #n`.

An item that cannot be classified (state or checks unreadable, mergeability still unknown) is listed as "check by hand" with its link. There is no cap on the number of lines. When no category has an item, print "Nothing to do: nothing is waiting on you."
