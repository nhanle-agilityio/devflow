# devflow — design

A Claude Code plugin (2.8.0; `version` in `plugin.json` and `marketplace.json`, history in `CHANGELOG.md`) with nine project-agnostic commands, plus `/devflow:init` (and `init --upgrade`) for setup:

1. **`/devflow:spec`** — idea → analyse → grill-me → spec PR (risk per task) → Gate 1 (human merges; this approves the risk levels) → GitHub issues labelled ready and `risk:low|high`.
2. **`/devflow:next-task`** — pick up to N ready issues → claim → branch → plan on the issue → implement (QA and dev agents in parallel when the plan allows it, else test first) → checks → verify → review → open PR labelled with its risk, stacked on a parent PR when needed. Runs in the user's checkout, or in its own worktree with `--isolated`; `--chain` runs a lane.
3. **`/devflow:dispatch`** — split the ready issues into non-colliding lanes and start one background session per lane.
4. **`/devflow:sync`** — keep those PRs mergeable: retarget, update behind branches, resolve conflicts, address review threads.
5. **`/devflow:answer`** — answer the questions that blocked an issue; record them in the spec (PR) and the issue, set it ready again.
6. **`/devflow:accept`** — after merge, check the shipped behaviour against the spec's acceptance criteria on a fresh checkout of the base; gaps become issues.
7. **`/devflow:release`** — merged devflow PRs → semver version → grouped notes with a risk section → GitHub release (draft by default).
8. **`/devflow:report`** — demo-ready trace page of one spec, from GitHub data.
9. **`/devflow:doctor`** — health check of the setup; `--fix` repairs what the user confirms.

Merging is done by a human, or for `risk:low` PRs by the merge gate GitHub Action (`devflow-merge-gate.yml`). Claude never merges.

Nothing in the plugin knows about a specific stack. Project mechanics live in `.claude/devflow.json`; project rules (architecture, conventions, "Never" list) live in the project's `CLAUDE.md`. Skills read both and never restate them.

## Principles

- **Deterministic where it matters.** The loop and the order of stages in `next-task` are a Workflow script (`workflows/next-task-engine.js`), not prose. Safety rules are hooks, not instructions.
- **Claude never merges.** The plugin opens PRs and pushes its own feature branches, never merges, never pushes to the base branch, never force-pushes (except `--force-with-lease` on its own branch). Who merges is decided by risk: a human for `risk:high` and unlabelled PRs; the merge gate Action (outside Claude, own token) for `risk:low` PRs once its checks are green.
- **Risk is judged early and enforced late.** The spec judges each task against `risk.highWhen` / `risk.highPaths` (unsure → high) and the human approves the levels at Gate 1. The engine only ever escalates to high, deterministically, when changed files match `risk.highPaths`. A missing label counts as high.
- **No reliance on GitHub paid features.** Target repos may be private on GitHub Free: no branch protection, no required checks, no native auto-merge. The merge gate is a plain Action that does the checking itself.
- **Model tiers.** Opus plans and reviews; Sonnet writes the per-issue plan, implements and ships (it writes the PR body reviewers read); Haiku runs mechanical steps (selecting, claiming, branching, running checks, blocked clean-up).
- **GitHub via the GitHub MCP server** (issues, labels, PRs, comments). `gh` is optional, never required. Adding a missing label to an issue creates it.
- **Merged state comes from one PR read or from git, never from a list.** The GitHub MCP list and search tools report `merged: false` for merged PRs, so every skill and the engine treat a PR as merged only when `pull_request_read` (method `get`) returns a non-null `merged_at`, or `git merge-base --is-ancestor <head sha> <remote>/<baseBranch>` succeeds after a fetch. Gate merges are told from human merges by the gate's marker comment or commit trailer.
- **Stack-agnostic verification.** `http` (API calls against the dev server), `browser` (Playwright MCP, or Claude in Chrome if that is what the user has) and `none`. A project enables any subset.
- **All committed content is English.** No `Co-Authored-By` or AI attribution in commits or PRs, unless the project's CLAUDE.md says otherwise.
- **Never write the review bot's at-sign handle into issues, PRs, comments or replies.** Repos that use `anthropics/claude-code-action` start a job on it. No stage posts a re-review trigger: pushing commits re-runs the review (`synchronize`). The handle appears only in the `claude.yml` template, as its trigger.

## `/devflow:init`

`disable-model-invocation: true`. Sets a project up once; idempotent (re-running shows a diff of proposed changes).

1. Read the repo: git remotes (find the GitHub one), default/current branches, `package.json` scripts, `Makefile`, `pyproject.toml`, lockfiles, framework config, `CLAUDE.md`, existing `.github/workflows`.
2. Propose a filled `.claude/devflow.json` (explain each detected value and where it came from). Ask the user to confirm or edit with AskUserQuestion for anything ambiguous (which remote, base branch, dev server command, verify modes). Write it plus `devflow.schema.json`.
3. Check the CLAUDE.md has what the workflows rely on (conventions, test approach, "Never" list). List gaps; offer to draft additions, never edit CLAUDE.md without a yes.
4. Risk and merge gate (AskUserQuestion, recommended option each time): `risk.highWhen` (show defaults), `risk.highPaths` (globs for auth, migrations, payments, CI config), `mergeGate.enabled` (default false, `dryRun` true), `mergeGate.requiredChecks` (job names found in `.github/workflows/*` plus `devflow/review`), `testing.e2eFramework` (true only when an automated e2e setup exists; say which signal), `spec.testMatrix` / `spec.qaModel`, `worktree.setup` (proposed from the detected tooling; `worktree.dir` stays `.claude/worktrees` unless the user wants another place), `dispatch.maxLanes`.
5. Install mode for the review check and the merge gate (one question): **reusable** (recommended), thin callers from `templates/github/callers/` that `uses:` this repository's `devflow-review.yml` / `devflow-merge-gate.yml` (`on: workflow_call`) at the tag `v<plugin version>` (`{{DEVFLOW_REF}}` replaced; the tag must exist); or **copy** (fallback), the full workflows plus `devflow-merge-gate.cjs`. A private devflow repository must allow Actions access from the user's repositories (Settings > Actions > General > Access), and its gate needs `DEVFLOW_READ_TOKEN` to read the script. Then offer (each a separate yes) the review, the gate (filling the `workflow_run` workflow list with the project's CI workflow names) and `claude.yml` (always a copy) when absent (otherwise show a diff). Tell the user the setup each needs (secrets `CLAUDE_CODE_OAUTH_TOKEN`, `DEVFLOW_GATE_TOKEN`; allow merge commits; gate on the default branch; see the README checklist). Add the worktree dir to `.gitignore` (diff, then a yes). Background sessions cannot answer permission prompts and a plugin cannot grant permissions, so init generates the allow list with `bin/devflow-setup allow` from `checks`, `verify`, `worktree.setup` and the remote (specific prefixes only: no bare interpreter, shell, runner or wrapper rule; runners keep flags and tool up to the first path or glob, a concrete script operand stays; inline-code flags and wrappers give no rule and are returned in `manual`; `curl` is scoped to `verify.devServer.url`'s origin when set), merges it into `.claude/settings.json` after a diff and a yes, and writes no deny rules (the guard covers merging, force pushes, protected branches, destructive git and `git add -A`).
6. Remind the user what the plugin hooks do and that `/devflow:doctor` lists project copies the plugin now owns.

The config is written with `devflowVersion` = the installed plugin version. The newer keys (`dispatch.ignoreHotspots`, `scan.ignore`, `verify.lock`, `notify`, `release`, `accept`) are mentioned with their defaults; only `notify.push` is asked.

**`/devflow:init --upgrade`.** For a project that already ran init (clean tree, config present). Reads the plugin version and the project's `devflowVersion`; compares byte for byte every installed template (the three workflows, `devflow-merge-gate.cjs`, `devflow.schema.json`, which upgrade keeps managing; a reusable caller is compared with `callers/` at the new tag, so upgrading moves the tag; templates never installed are skipped) and lists the drifted ones and the config keys missing from the project. Because devflow cannot tell whether the project edited a file after install, every drifted file gets a diff and its own yes; a declined file stays. The gate workflow's `workflow_run` list is kept. After the yes: branch `chore/devflow-upgrade-<version>`, copy the accepted files, set `devflowVersion`, validate the config against the new schema, commit `chore(devflow): upgrade templates to devflow <version>`, push, open a PR labelled `devflow` + `risk:high` (it touches `.github/**` and `.claude/**`, so a human merges; a compare link if PR creation fails). Never merges, never pushes to the base.

## `/devflow:spec <idea or path to a brief>`

`disable-model-invocation: true`. Designed to run in a cloud session (claude.ai/code) on the repo, works locally too. Steps, each announced with its number:

1. **Analyse.** Read `.claude/devflow.json`, `CLAUDE.md`, and the code the idea touches. Produce a short analysis: current behaviour, affected areas (backend/frontend/infra/data), risks, unknowns. Do not write files yet.
2. **Grill.** Invoke the `grill-me` skill on the idea plus the analysis. Keep going until every unknown is decided or explicitly deferred. If `grill-me` is not available, run the same interview inline: one question at a time, each with a recommended answer.
3. **Spec + tasks.** Create branch `spec/<slug>` from `<remote>/<baseBranch>`. Write `<specDir>/<YYYY-MM-DD>-<slug>.md` from `templates/spec.md`: problem, goals/non-goals, decisions (with the grill answers), design (API contracts, data model, UI screens and states, mocks if any — mocks go in `<specDir>/<slug>/`), risks, and the **task list**. Each task: stable id `T1..Tn`, title, type, `area`, depends-on, acceptance criteria written as checkable behaviour (API: request → response; UI: user action → visible result), files/areas in scope, test plan, `needs-e2e` yes/no, size S/M (split anything bigger), **risk** `low|high` with a one-line reason (judged against `risk.highWhen` and `risk.highPaths`; unsure → high), and **hotspot files** other tasks are likely to touch (`/devflow:dispatch` uses them to plan lanes).
4. **Test matrix (QA).** Skipped when `spec.testMatrix` is false. A QA agent (Agent tool, model `spec.qaModel`, default opus) gets only the spec file and `CLAUDE.md`, not the grill conversation, so it tests what the spec says rather than what was meant. It returns test-case rows (id `T<n>.<k>`, criterion, case happy/error/edge/boundary, Given/When/Then, level unit/integration/http/e2e, priority must/should; every criterion has a must row), the criteria it cannot test as written, and cases the spec leaves undecided. Those go back to the user one at a time with a recommended answer; the spec is updated and QA runs again, at most 2 rounds, leftovers under Risks. The rows go into the spec's Test matrix and each task's test plan points at them. Opus is the default because the value of the step is in spotting what the spec does not say, and the matrix is copied into every issue, so a miss repeats; it runs once per spec, so the cost is small.
5. **Spec PR.** Commit `docs(spec): <title>`, push the branch, open a PR to `baseBranch` titled `spec: <title>`, body = summary + task table (incl. risk and reason) + test matrix size and QA questions resolved/open. No need to ask before pushing the spec branch or opening the PR.
6. **Gate 1.** Ask exactly one question (AskUserQuestion): "Spec PR <url> merged? Merging also approves the risk levels in its table." — options: merged / changes requested / abandon. Changes requested → read the PR review comments, update the spec on the same branch, push, ask again. Abandon → close nothing, stop. Merged → verify through MCP that the PR is merged; if not, say so and ask again.
7. **Issues.** Search existing issues for each task title first (no duplicates; re-running after a partial failure must be safe). Create one issue per task from `templates/issue.md`: title `[<slug>] T<n>: <task title>`, body with spec link (on baseBranch), acceptance criteria as a checklist, scope, test cases (the task's Test matrix rows, or the test plan when there is no matrix), `Depends on #<n>` lines (resolve task ids to issue numbers — create in dependency order), a Risk line and Hotspots section, labels `labels.ready` plus `labels.riskLow` or `labels.riskHigh` plus `labels.e2e` when needed plus `type:<type>`. Then comment on the spec PR with the issue list. Final message: table task → issue.

## `/devflow:next-task [limit | #issue ...] [--isolated] [--chain]`

`disable-model-invocation: true`. Entry point only; the work is the workflow.

Preflight (inline, fail fast with a clear message):
- `.claude/devflow.json` exists and parses; else tell the user to run `/devflow:init`.
- Working tree clean. Not isolated: current branch noted (restored after every issue; detached HEAD is refused). Isolated: a detached HEAD is fine, no start branch.
- `git fetch <remote> <baseBranch>` succeeds.
- GitHub MCP reachable (get the authenticated user).
- `gh` installed or not (`command -v gh`), passed as `ghCli`.

Flags: `--isolated` (own worktree) and `--chain` (the explicit issues are a lane: in the given order, each stacked on the previous one; needs explicit issues).

**Isolated setup** (before the workflow). Inside a linked worktree already (`git rev-parse --git-dir` ≠ `--git-common-dir`): use it. Otherwise `name` = `issue-<n>` or `lane-<n1>-<n2>...`; `git fetch <remote> <baseBranch>`; `git worktree add --detach <worktree.dir>/<name> <remote>/<baseBranch>` (an existing worktree at that path is reused only when clean); the EnterWorktree tool with that path (if unavailable: stop, tell the user to start with `claude -w`). Then run each `worktree.setup` command in order; a failure stops the run. The worktree is created by devflow, not left to background auto-isolation (see Verified behaviour).

**`claimId`**: `<timestamp>-<name>-<pid><random>` (`main` as name when not isolated); the pid and random suffix separate two sessions started in the same second on the same issue.

Then call the Workflow tool with name `devflow:next-task-engine` and `args = { config: <parsed devflow.json>, limit: <n or config default>, issues: [<explicit issue numbers>], startBranch: <current branch, "" when isolated>, prTemplatePath, isolated, chain, claimId, ghCli }`. `prTemplatePath` points at `templates/pr.md`; `bugTemplatePath` at `skills/spec/templates/bug.md`. When it returns: isolated and the worktree is clean with every created branch pushed → ExitWorktree and `git worktree remove <path>`; otherwise ExitWorktree and keep it, telling the user the path and why. Print the summary table from the result fields only: issue → PR (risk, and the PRs it is stacked on) / blocked (reason) / skipped (reason, including `already claimed` / `claimed by <id>`), plus a Notes column with the entry's `notes` joined by "; " verbatim. The skill adds no account of its own (timing, why something was or was not stacked): the engine states the facts, anything else would be a guess. If an entry says "GitHub MCP unavailable", say the run stopped there and `/devflow:doctor --fix` cleans up once GitHub is back. Say who merges: the merge gate for `risk:low` when enabled, a human otherwise.

**Notify** (last step, after the table). When `notify.push` is true and the PushNotification tool exists (else skip silently), send one message of at most 200 characters naming the repository: blocked issues (`notify.onBlocked`), else a `risk:high` PR waiting for a human (`notify.onHighRisk`), else the done count (`notify.onDone`); several that apply are combined. It is how background lanes are followed from a phone.

## Workflow `next-task-engine.js`

Plain JS, no `Date.now()`/`Math.random()`, no filesystem (the `claimId` therefore comes in as an argument). Within one run, tasks run **sequentially** in one working tree (the main checkout, or the worktree when `isolated`); parallelism is across sessions (see Parallel work). Every agent gets the config in its prompt. Every agent returns structured output (schemas below); a stage that fails marks the issue blocked and moves on to the next issue.

**Notes.** Each result row carries `notes`: facts the engine records as they happen (a lane that continued after an issue that did not ship, a resumed branch, a parent that merged meanwhile, QA tests that did not fail first, manual checks not passing). The skill prints them verbatim; `/devflow:report` and the summary rely on them instead of inferred stories.

**GitHub MCP stop.** Without `gh` (`ghCli` false) the MCP note tells every agent: if the MCP server is unavailable, stop and report starting with "GitHub MCP unavailable". `block()` recognises that marker (also from Claim's `problem`): no cleanup is possible, so it posts nothing, returns the row `blocked` with `mcpDown`, and the main loop skips every remaining issue with that reason. The stopped issue keeps its in-progress label and claim; `/devflow:doctor --fix` clears them.

Phases: `Select`, then per issue `Implement` (Claim, Branch, Integrate, Plan, Implement, Commit), `Check`, `Verify`, `Review`, `Ship`, then `Report`.

0. **Priority and triage** (deterministic, pure helpers): `priorityRank(labels, labels.priority)` is the index of the first listed label the issue has; no label counts as the entry ending in "normal" (after every entry when there is none). `orderIssues(issues, labels.priority)` orders the selection: dependencies inside the set first (Kahn), ties by effective rank then number, where an issue's effective rank is the best rank of itself and every issue that depends on it, so a critical child pulls its open parents forward; a cycle places the best remaining issue and goes on. A `chain` run keeps its given order. Issues labelled `labels.triage` are skipped in code (reason "needs-triage: a human sets it ready first") as well as in the Select prompt. Nothing is preempted: the order applies to the selection of one run.
1. **Select** (haiku, schema `{issues:[{number,title,labels,body,dependsOn:[int],parents:[{issue,prNumber,branch,inRun}]}], skipped:[{number,reason}]}`): explicit issues if given, otherwise open issues with `labels.ready`, not labelled inProgress/blocked/triage, no open PR referencing them. Dependencies: all `Depends on` issues closed → normal (`parents: []`); every open dependency has an open PR (`inRun: false`) or is selected earlier in this run without a PR yet (`inRun: true`, the engine fills in the PR once the parent ships) → **stacked** on all of them; an open dependency with neither, or an in-run parent that did not ship, skips the issue naming it. Order: parents first, then oldest; with `chain` and explicit issues, exactly the given order (an earlier issue of the same list is a parent only when there is a real `Depends on`; lane stacking is done by the engine). The agent returns up to 3×`limit` candidates; the engine works on `limit` of them (a skipped child does not count). `log()` what was skipped and why (no silent caps).
2. Per issue, in order:
   - **Claim** (haiku, schema `{taken, takenBy?, claims:[{commentId, claimId, createdAt}]}`): a two-call lock. Call 1 (claim): if the issue has an assignee or `labels.inProgress` / `labels.blocked`, return `taken` and change nothing (the issue is skipped as `already claimed`). Otherwise assign the authenticated user, add `labels.inProgress`, remove `labels.ready`, post `<!-- devflow-claim id=<claimId> -->` + `Claimed by devflow (<claimId>).`, re-read all comments and return every claim comment. The engine decides in code: our claim must be present (else blocked), and `pickClaimWinner` takes the earliest `createdAt`, ties by smallest comment id. Call 2 (release, haiku), only for a loser: delete just our own claim comment; labels and assignee belong to the winner; the issue is skipped as `claimed by <id>`. No two sessions can both pass, as long as GitHub's `created_at` order is the same for both readers.
   - **Branch** (haiku, schema `{ok, branch, problem?}`): `git status --porcelain` empty; `git fetch <remote> <fetchBranch>`; `git switch -c <branch> <parentRef>` (branch from `branchPattern`; works from a detached HEAD), where `parentRef` is `<remote>/<baseBranch>`, or `<remote>/<parent PR branch>` when stacked. An existing branch name is a failure (blocked at stage Branch), except two cases. A leftover from a run blocked at Plan (a local branch with no commits of its own, not on the remote) is recreated from `parentRef`. **Resume**: a branch with commits whose scope is this issue (a run blocked after Plan) is continued: switch to it (tracking the remote one when it is only there), `git merge --no-edit <parentRef>` (a conflict is aborted and blocks); Branch returns `resumed` and the earlier commits. Commits of another issue, or a dirty state, still block. A resumed branch skips parallel QA (the QA tests may already be committed): one Implement agent gets the earlier commits, keeps what still matches the spec, issue and Decisions, and changes only what does not. Touches no GitHub state.
   - **Plan** (sonnet, after Branch and Integrate, schema `{status: ready|blocked, plan, questions:[string, each starting "[BA] " or "[QA] "], qaFiles:[], devFiles:[], specRead}`): reads the spec (`git show <baseRef>:<path>`; `specRead` required when the issue links one), the acceptance criteria, CLAUDE.md and the touched code. Writes no code. Posts the plan as an issue comment whose first line is `<!-- devflow-plan -->` (edited in place if one exists): Files to change; Tests (a row per Test cases id); Risks; Order of commits; Open questions. `qaFiles` = test files the QA agent owns (the tests for the issue's Test cases rows), `devFiles` = files the dev agent will change; a file in both blocks the issue at Plan ("ownership overlap"). A `## Decisions` section in the issue body overrides the spec where they differ (Plan and Implement prompts). Nobody approves it. `blocked` (BA questions: spec gaps; QA questions: Test cases rows not testable as written) → the issue is blocked at stage Plan before any code, with the merged questions comment (below). Otherwise the plan text is handed to Implement, which follows it and records deviations under `assumptions`.
   - **Implement, single agent** (`parallelQa` false, or no `qaFiles` such as docs-only issues; sonnet, schema `{status: done|blocked, summary, commits:[sha+msg], filesChanged, assumptions:[], outOfScope:[], blockedReason?}`): read the issue and the linked spec; follow CLAUDE.md. For behaviour changes and bug fixes: commit a failing test first (`test(<scope>): ...`), confirm it fails for the right reason, then the implementation (`feat|fix(<scope>): ...`). When the issue has a Test cases table, write a test for every `must` row, traceable to its row id: a naming pattern stated in the issue, spec or plan is followed exactly (no extra prefix; Review flags a mismatch as a warning), otherwise `test_t<task>_<n>_...` or a `# T1.2` comment. The QA agent follows the same rule. With `testing.e2eFramework` false, `e2e` rows get no committed test: Verify covers them. Stage files by name. Stay inside the issue scope; record anything else in `outOfScope`. Ambiguity that changes behaviour and is not answered by the spec → `blocked` with the question (no guessing on contracts); minor ambiguity → decide and record in `assumptions`.
   - **Manual checks** (both Implement variants; schema field `manualChecks:[{rowId, result: pass|fail|not-run, evidence}]`): a Test cases row that cannot be an automated test (a manual or review checklist, e.g. a Makefile target or a README line) is checked by hand (in a scratch directory when it writes files) and reported per row with the command and relevant output. A `must` row may be `not-run` only when it truly cannot run, with the reason. The engine merges them per row (a later check after a fix replaces the earlier one). Review gets them: a `must` row neither tested nor manually passed, and a failing manual check, are warnings. Ship puts them in the PR's Tests section as a table; rows not passing are added to the result notes.
   - **Implement, parallel QA** (`nextTask.parallelQa` true and `qaFiles` non-empty): two sonnet agents run in parallel in the same checkout, neither commits. **QA** (schema `{status: done|blocked, tests:[{rowId, test}], filesChanged, questions:[], specRead}`) writes the acceptance tests for every `must` Test cases row from the spec and the issue only (black box: it never reads the implementation diff) and touches only `qaFiles`. **Dev** (the Implement schema above) writes the implementation and touches no `qaFiles`; it may add extra tests in other files. Their questions are merged (below). The engine then blocks the issue if QA changed a file outside `qaFiles` or dev changed a qaFile.
   - **Commit** (haiku, parallel QA only): commit the QA tests first (`test(<scope>): ...`), stash the implementation and confirm the new tests fail, restore it and commit the implementation (`feat|fix(<scope>): ...`). Stage files by name. Schema `{ok, commits, failedFirst, failureNote}`; tests that pass without the implementation do not block, the engine logs it and adds it to the PR's assumptions so the review sees it. Fix rounds (Check, Verify, Review) never edit `qaFiles`; a fix agent that thinks a QA test is wrong returns blocked with a `[QA]` question.
   - **Root cause** (fix issues only; `isFixIssue`: a `type:fix`, `type:bug`, `bug` or `fix` label, an `accept.labels` label, a `Gap:` or `fix:` title, or a body with `## Introduced by`): Implement returns `rootCause {cause, introducedBy, whyMissed}`; when it is missing, one Fix round asks for it, then the PR says "unknown" and the result notes it. That round never blocks the issue (an agent that dies or returns blocked is noted, and the PR ships with "unknown"), except when it edits a QA file. Ship writes the Root cause, Introduced by and Why it was missed sections.
   - **Check** (haiku, schema `{passed, failures:[{check, output}]}`): run every `checks[].run` in order, report only failures (trimmed output). If failed: **Fix** (sonnet) with the failures, then Check again; up to `maxFixRounds`. Still failing → blocked.
   - **Verify** (sonnet, schema `{ran, mode, steps:[{action, expected, actual, pass}], notes}`): only if `verify.modes` is non-empty and the issue has `labels.e2e`, the diff touches UI, or the issue's Test cases table has a row with level `http` or `e2e`. Start the dev server in the background, wait until `url` answers (≤ `readyTimeoutSec`), walk every acceptance criterion and every Test cases row with level http or e2e: `http` with curl, `browser` with the configured browser tool (navigate, act, read the page; take screenshots for the agent's own check). Stop the server. With `verify.lock` (default true) the agent first takes a machine-wide lock, `mkdir "$(git rev-parse --git-common-dir)/devflow-verify.lock"` (retry every 10 s for up to 10 min; a lock older than 30 min is stale and removed; still busy → `ran=false`, "verify lock busy"), so parallel lanes never fight over the dev server port, and always removes it afterwards. Failures → one Fix round (sonnet) → Check → Verify again; still failing → blocked.
   - **Weakened-checks scan** (haiku, before every Review round, schema `{scanned, hits, error?}`): runs `node "<pluginRoot>/bin/devflow-scan" <parentRef> .claude/devflow.json` and returns only its output. The script runs `git diff --unified=0 <parentRef>...HEAD` itself and scans it with the engine's pure `scanWeakenedChecks(diff, checkConfigGlobs(checks))` (loaded through the `args.exports` hook, so there is one implementation), so no diff travels through an agent. `parseDiff` reads `--- ` / `+++ ` as file headers only before a file's first `@@`. It finds: added `# noqa`, `type: ignore`, `pyright: ignore` / `pylint: disable`, `pytest.mark.skip|skipif|xfail`, `unittest.skip`, `it|test|describe.skip|only`, `xit` / `fit`, `eslint-disable`, `@ts-ignore|nocheck|expect-error`, empty `except` (one line, or `pass` on the next line), empty `catch {}`, Go `t.Skip|Skipf|SkipNow` (in `_test.go` files), `@Disabled` / `@Ignore`, Rust `#[ignore]`, `//nolint` and `# rubocop:disable`; hollow assertions (`assert True`, `expect(true).toBe(true)`, `assert.ok(true)`) in test files (`src/test/**`, `*Test.java`, `*Tests.java`, `*Test.kt`, `*_spec.rb` and `*_test.rs` count as test files); none of these line patterns run on prose or docs files (`.md`, `.mdx`, `.txt`, `.rst`, `.adoc`, anything under `docs/`); in test files a deleted file, fewer test definitions or fewer assertions than before; and any edit to a file that configures the checks (`.claude/devflow.json`, Python/JS/Go linter, type checker and test runner configs, `.pre-commit-config.yaml`, `.github/workflows/*`, `**/Makefile` when any simple command of a check (split at `&&`, `||`, `;`, `|`) runs `make`, `.github/scripts/**`, `.github/actions/**`, and script paths named in `checks[].run`). The optional third argument `ignoreGlobs` (config key `scan.ignore`, globs matched with `globToRegExp`, default `[]`; anything but an array means none) skips every matching file with no rule applied (line patterns, deleted test file, removed tests and assertions, check configuration); `bin/devflow-scan` reads it from the config and adds `"ignored": [paths]` to its output only when it skipped a file. `.claude/devflow.json` is exempt from ignoring, so a change that adds a glob to the list is itself a `check configuration changed` hit (and, under `risk.highPaths`, a high-risk path at the merge gate). `package.json` and `conftest.py` are not on the list, since most of their edits are dependencies and fixtures; instead, in any `package.json`, a changed script-like entry (`test`, `lint`, `build`, ... with a non-version value) or the opening of an embedded tool config (`jest`, `eslintConfig`, `scripts`, ...) is one `check configuration changed` hit, and an added `collect_ignore` / `pytest_ignore_collect` is a `collection ignored` hit.
   - **Review** (opus, read-only, schema `{verdict: pass|changes, findings:[{severity: critical|warning|suggestion, file, line, problem, fix}], acceptedWeakenings:[{file, line, reason}]}`): review `git diff <parentRef>...HEAD` (so a stacked PR shows only its own changes) against the issue's acceptance criteria, the spec and CLAUDE.md; correctness first, then tests (does each change have a test that fails without it; a `must` Test cases row without a traceable test is a warning, except `e2e` rows when `testing.e2eFramework` is false), then scope creep, then the out-of-scope list (an item that leaves an acceptance criterion or a `must` row unmet is critical: an AC violation written as "left as is" is in scope), then the scan hits. Every hit is critical unless the reviewer lists it in `acceptedWeakenings` because the issue itself asks for it; the engine adds a critical finding for each hit that is neither reported nor accepted, and a `pass` verdict does not override it. Critical/warning → Fix (sonnet) → Check → Review again, up to `maxReviewRounds`; suggestions go to the PR body, not fixed. A fix that implements an out-of-scope item returns it in `outOfScopeDone` and the engine drops it from the list.
   - **Risk** (deterministic, in the engine, no agent): level = the issue's risk label (`unknown` if none, treated as high); reason = the issue body's `Risk:` line. If any changed file matches a `risk.highPaths` glob, the level becomes high and the reason names the file. Accepted scan hits still in the last reviewed diff, or a scan that could not run (no `pluginRoot`, the agent died, or the script reported `scanned: false`), also make it high, with the hits named in the `Risk:` line and the result notes. So does a required verification that could not run (`ran: false`: lock busy, dev server never started, tool unavailable): the engine still continues, but the first line of the verify notes is named in the `Risk:` line and the result notes, joined with any scan reason by "; ". An escalation also sets `labels.riskHigh` on the issue.
   - **Ship** (sonnet): push the branch (`git push -u <remote> <branch>`), open a PR via MCP with `templates/pr.md` filled from the stage results (what, how, risk line, tests, verification evidence, assumptions, out of scope, `Closes #<n>`). The PR base is `baseBranch`, or the parent PR's branch when stacked (the body then says it retargets when the parent merges). Label the PR `labels.devflow`, `labels.riskLow|riskHigh` and, when stacked, `labels.stacked`; add `labels.review` to the issue and remove `labels.inProgress`. Each remaining out-of-scope item that is a real problem (not a remark) becomes a follow-up issue `[follow-up #<n>] ...` from the bug template (`args.bugTemplatePath`) labelled `labels.triage` (default `needs-triage`, never ready: a human triages it), with a comment suggesting a priority and a risk with reasons, unless an open issue covers it, and is linked in the PR's Out of scope section; Ship returns them in `followUps` and the engine notes them. Return `{prNumber, url, followUps}`. When stacked on one parent, Ship first re-reads the parent PR: if the gate merged it meanwhile (and deleted its branch), the PR targets `baseBranch` without the stack line or label and Ship returns `unstacked`. Branch and Integrate apply the same rule when a parent branch is already gone.
   - **Merged questions.** Questions from Plan (BA, QA), from the QA agent and from the dev agent are collected into ONE issue comment whose first line is `<!-- devflow-questions -->`: numbered, each tagged [BA], [QA] or [Dev], ending with "Answer with /devflow:answer #<n>, or reply on this issue with numbered answers." The issue is blocked once with all of them, not once per role.
   - **On blocked at any stage** (haiku): commit nothing further; if the branch has commits, push it so work is not lost; comment on the issue with the stage, reason and question (the questions comment above when there are questions); delete the run's own `<!-- devflow-claim id=... -->` comment; label `labels.blocked`, remove `labels.inProgress`; `git switch <startBranch>`.
   - After each issue: `git switch <startBranch>` so the next one starts clean. Isolated: no restore; Ship and Blocked stay on the branch (the worktree is dedicated, no switch, no stash).
   - **Chain** (`chain` true): each issue is stacked on the last issue of the lane that shipped (added to its parents unless already one), so the lane is a stack: each branch starts from that branch and each PR targets it. An issue that does not ship (blocked, or skipped, including claimed elsewhere) does not stop the lane: the next issue stacks on the last shipped one, or starts from the base when none shipped; only an issue with a real `Depends on` the failed one is skipped. Overlapping changes with the failed issue's branch, if it is finished later, are left to the gate and `/devflow:sync`.
3. **Report**: return `[{issue, status: pr|blocked|skipped, url?, prNumber?, risk?, stackedOn?, reason?}]`.

**Stacking.** The engine keeps a map of issues that shipped in this run (issue → PR number and branch) to resolve in-run parents. One parent: the branch starts from the parent's branch and the PR targets it. Several parents: Claim branches from the base, then **Integrate** (sonnet, schema `{ok, integrationSha, merged, problem}`) merges every parent branch with merge commits (no rebase), resolves conflicts between them, runs the checks and returns `integrationSha`; that SHA is the parentRef for Implement, Fix, Review and Blocked, and the PR targets the base with a "Stacked on #a and #b" line. The gate holds every PR whose linked issue still has an open `Depends on`.

**Parallel work.** One ticket per session, each session in its own worktree, started by hand (`/devflow:next-task #n --isolated`) or by `/devflow:dispatch`.

- *Lane planner* `bin/devflow-lanes` (node, no dependencies; pure function `planLanes` exported for tests). Input `{maxLanes, ignoreHotspots:[], issues:[{number, hotspots:[], dependsOn:[]}]}` on stdin; output `{lanes:[{issues, sharedHotspots}], deferred:[{issues, reason}], ignoredHotspots, warnings}`. Hotspots matching `ignoreHotspots` (exact path, or glob with `*` and `**`; `[]` ignores none) are dropped before grouping and echoed in `ignoredHotspots`: docs files like the README and CHANGELOG are touched by most tasks and their conflicts are small (the gate's branch update or `/devflow:sync` resolves them), so they would otherwise merge every task into one lane. Union-find: two issues join when they share a hotspot (exact, case-sensitive, trimmed path; transitive) or one depends on the other and both are in the set (dependencies outside the set are ignored). Inside a lane: topological order, parents first, ties by smallest number; a cycle falls back to number order with a warning. Lanes sorted by their smallest issue number; lanes beyond `maxLanes` (default 3) go to `deferred` with reason `over maxLanes (N)`. Invalid input: message on stderr, exit 1. Why this shape: tasks that touch the same files share a lane and stack on each other, so parallel lanes never touch the same files and never conflict; stacking inside a lane replaces rebasing and merge conflicts.
- *`/devflow:dispatch [max lanes]`* (`disable-model-invocation: true`, no commits, never merges). Preflight: config, GitHub MCP, `claude --version`, clean tree. Collect: open `labels.ready` issues, not in-progress or blocked, without an open PR that closes them; read `Depends on`. An issue whose open dependency has no PR and is not in the set is not schedulable and is listed as "waiting for #N". Build `{number, hotspots, dependsOn}` per issue (hotspots from the body's `## Hotspots` bullets, backticks stripped, bare "None" skipped). `maxLanes` = argument, else `dispatch.maxLanes`, else 3; `ignoreHotspots` = `dispatch.ignoreHotspots`, default `["README.md", "CHANGELOG.md"]`. Print the plan (lanes, order, shared hotspots, ignored hotspots, deferred, waiting), continue without asking again, and start lane n with `claude --bg "/devflow:next-task #a #b --chain --isolated"` (plus `--plugin-dir <dispatch.pluginDir>` when set; `--chain --isolated` even for a one-issue lane). If `claude --bg` fails, stop starting lanes and print the `claude -w lane-<n> "..."` command for the failed and remaining lanes. Report: lane → session id → issues; follow with `claude agents`, `claude logs <id>`, `claude attach <id>`.
- *Safety nets.* The claim (above) is what makes a double start harmless: a second session on the same issue skips it. A broken lane stops at the first issue that does not ship. Worktrees are created under `worktree.dir`, ignored by git, and removed only when clean and fully pushed.

**Verified behaviour** (spike on the real machine, not assumed):

- `claude --bg --plugin-dir <dir> "/plugin:skill"` expands the plugin skill in the background session.
- A `claude --bg` session did **not** move into a worktree by itself (its Bash ran in the main checkout). So devflow creates the worktree itself (`--isolated`) and does not rely on background auto-isolation.
- After EnterWorktree, Workflow agents run in the session's worktree directory.
- `claude --bg` needs a trusted workspace ("Workspace not trusted" otherwise), and the background session cannot answer permission prompts, so the project needs allow rules (or an auto permission mode); `/devflow:init` offers them.
- A fresh worktree needs its own setup (`worktree.setup`, e.g. `make setup`, took ~3 s on TaskBoard).

**Test hook.** `args.exports === true` returns the pure helpers (`parseDiff`, `scanWeakenedChecks`, `checkConfigGlobs`, `globToRegExp`) before anything else runs. They are function declarations, so they are hoisted, and they take every input as a parameter.

**Spec read.** `specPathFor(issue)` takes the first `<specDir>/…md` path from the issue body. Implement starts with `git show <baseRef>:<path>` and must return `specRead` containing the path; otherwise one Fix round re-checks the change against the spec, and a second miss blocks the issue. Review is pointed at the same path.

## `/devflow:sync [#pr ...] [--unattended]`

Not `disable-model-invocation`: a scheduled `/loop` prompt arrives as plain text and Claude can only run a skill through the Skill tool, which that flag blocks, so `/loop 15m /devflow:sync` could never run. Sync is the one skill meant to run unattended; its description limits model invocation to a user request or a `/loop` prompt naming it. An unattended run (`--unattended`, the form to use in a loop, or a run evidently started by `/loop`) asks nothing: a thread needing a product decision stays unresolved and is listed as "needs a human". It works in a temporary worktree of `<remote>/<baseBranch>` (removed in every case, never touching the user's checkout), stops at once with "nothing to sync" when there are no targets, and keeps the round limit as its safety stop. Interactive runs are unchanged. Replaces `/devflow:address-reviews`. Default targets: open PRs labelled `labels.devflow` and authored by the current user; explicit `#pr` numbers override. Needs a clean working tree; the starting branch is restored at the end. Fork PRs are skipped. PRs are processed parents before children. Only new commits and normal pushes: no rebase, no force push, no merge.

Per PR:
1. **Retarget.** If the PR is stacked and its parent PR is merged (or the base branch is gone), change its base to `baseBranch` (`update_pull_request`) and remove `labels.stacked`.
2. **Update when behind.** If behind and it merges cleanly, `update_pull_request_branch`.
3. **Conflicts.** Merge `<remote>/<base>` into the branch (a merge commit, never a rebase). Resolve each conflict from the linked issue and spec, keeping both behaviours when compatible; run `checks`; commit `merge(<scope>): sync with <base>`; push. Then remove `labels.blocked` from the PR and its issue (the gate adds it on conflict), unless something else blocks the issue. If a conflict cannot be resolved with confidence or checks fail: `git merge --abort`, label the issue blocked, comment with the files and the one question for a human.
4. **Review.** Unresolved, actionable threads are classified fix / answer / won't fix (reason, citing CLAUDE.md or the spec); a thread needing a product decision goes to the user. Fixes are new commits (`fix(<scope>): address review - <what>`), `checks` must pass, push, then reply on every thread. The merge gate treats a thread as answered when its last comment is by the PR author, so the reply is what unblocks it. No re-review comment is posted: the push re-runs the review.
5. **Round limit.** A round is a run of step 3 or 4 that changed or answered something. Rounds are counted by the hidden marker `<!-- devflow-sync -->` in earlier comments; at `nextTask.maxReviewRounds` the PR is left for the user. After a round, one marker comment with a one-line summary is posted. Steps 1 and 2 are not rounds.
6. Switch back; summary table PR → retargeted / updated / conflicts / threads fixed, answered, won't fix / rounds left.

## `/devflow:answer #issue [1: answer; 2: answer ...]`

`disable-model-invocation: true`. Unblocks an issue that the engine blocked with questions. Needs a clean working tree. GitHub via the MCP server. Never merges, never pushes to `baseBranch`.

1. **Questions.** Find the latest issue comment starting with `<!-- devflow-questions -->`; none → nothing to answer, stop.
2. **Answers.** From the arguments (`1: ...; 2: ...`), else from comments by humans (not bots) posted after the questions comment. Every question needs an answer; otherwise list the unanswered ones and change nothing.
3. **Spec (BA role).** Branch `docs/<issue>-answers` from `<remote>/<baseBranch>`; update the spec so each decision sits in the section it belongs to and append `- <date> (#<issue>, Q<k>): <question> → <answer>` to its `## Decisions` section (created at the end if missing). Commit `docs(#<n>): record answers to open questions`, push, open a PR to `baseBranch` labelled `devflow` + `risk:low` (`risk:high` if the spec path matches `risk.highPaths`), `Refs #<n>` (not Closes). If PR creation fails, the user gets a pre-filled compare link.
4. **Issue body (BA role).** Append or extend the issue's `## Decisions` section with the same entries (Plan and Implement treat it as overriding the spec); an answer that changes an acceptance criterion or a Test cases row updates that line, marked "(updated by /devflow:answer)". It is the human's decision, not an edit to make a test pass.
5. **Unblock.** Delete every `<!-- devflow-claim id=` comment, remove the assignee devflow set, remove `labels.blocked` and `labels.inProgress`, add `labels.ready`, post one comment (answers, spec PR link, "Ready again: run /devflow:next-task #<n>").
6. **Report.** Table question → answer, the spec PR, the issue's labels. A branch left over from a run blocked at Plan is reused or recreated by Branch; a branch with commits from a run blocked later is not, and is handled by hand.

## `/devflow:accept <spec path or slug>`

`disable-model-invocation: true`. The BA step after merge: does what shipped match what the spec promised? Changes no tracked file, makes no commit, never merges. Preflight: config with `verify.devServer` and non-empty `verify.modes` (else acceptance cannot run), GitHub MCP, clean tree, fetch.

1. **Resolve.** The spec is read from `<remote>/<baseBranch>` only (not there → its PR is not merged, stop). List tasks, criteria and the Test matrix rows with level `http` or `e2e`; find the issues whose body links the spec (matched to tasks by `T<n>` in the title) and their closing PRs. Only merged issues are accepted; none merged → nothing to accept.
2. **Fresh worktree** of `<remote>/<baseBranch>` under `worktree.dir` (`accept-<slug>`), `worktree.setup` run in it: what shipped, not the user's checkout.
3. **Verify lock** (`verify.lock`), same lock as Verify.
4. **Walk** every criterion of every merged task plus those matrix rows with the allowed `verify.modes` (curl, or the configured browser tool), run with `accept.model` (`sonnet` default, an Agent of that model when the session differs). Result per criterion: `pass`, `fail` or `not checkable`, with expected versus actual evidence. The dev server, lock and worktree are always cleaned up.
5. **Gaps.** Each `fail` without an open duplicate is drafted from the bug template `skills/spec/templates/bug.md` as an issue `[slug] Gap: ...` (Context, Expected, Actual, Repro, Introduced by, a suggested Risk, Acceptance criteria, Scope, Test cases, Dependencies; labels `labels.triage` and `accept.labels`, no ready, risk or priority label), followed by a comment suggesting a priority and a risk with reasons. A human sets those labels and ready. One yes for the whole batch; declined → none created. `not checkable` items are listed for a human and get no issue.
6. **Report.** One comment starting `<!-- devflow-accept -->` on the spec PR (table, counts, issues left out, gap links), edited in place on a re-run. Gap issues are picked up by `/devflow:next-task` once a human sets them ready; `/devflow:release` includes the result.

## `/devflow:release <spec | since <tag> | all> [--version X.Y.Z]`

`disable-model-invocation: true`. Config `release`: `tagPrefix` (`v`), `draft` (true), `deploy` (empty), `notesFrom` (`prs`). Never merges, never pushes tags from the shell; the GitHub release creates the tag.

1. **Collect** the merged PRs labelled `labels.devflow` with base `baseBranch`: for a spec, the PRs closing its issues plus the spec PR; for `since`, those merged after the tag (latest tag with the prefix when none is named); for `all`, every one (the proposed default when no tag exists). `spec:` PRs are included. Refuse while one of the spec's issues has an open PR (unless the user says release anyway); an issue with no PR is listed as not shipped.
2. **Version.** `--version` wins (stop if the tag exists); otherwise propose the next semver from the Conventional Commit types: a breaking change (`!` or a `BREAKING CHANGE` footer) major, any `feat` minor, otherwise patch; `0.1.0` with no earlier tag. The user confirms.
3. **Notes** in English: **What's new** first (client-facing, grouped by spec, no numbers or internal names), then a **Changelog** with Features, Fixes (those whose linked issue has the first `labels.priority` label first, marked critical), Docs (including `spec:` PRs), Chores (empty ones omitted, one line per PR); **Risk** (each `risk:high` PR and who merged it, or "No high-risk changes.", plus gate versus human: the gate marks its merges with a `<!-- devflow-gate-merged -->` comment and a `Merged-by: devflow merge gate` trailer; older PRs show "merger unknown (gate or owner)" when the gate token owner merged); **Acceptance** (counts and gap links from the `<!-- devflow-accept -->` comment, or "not run"). Shown for a yes.
4. **Create the release** with the MCP server (title = tag, target = the base head commit, `draft` per config). Without a release tool: a pre-filled `releases/new` link and the notes.
5. **Deploy** only when `release.deploy` is set, and only after a separate explicit yes (a yes for the release is not one for the deploy; a draft has no tag yet, which is said). Exit code and the last 20 lines are reported; no retry.

## `/devflow:report <spec path or slug>`

`disable-model-invocation: true`. Read-only on GitHub and the repository; posts nothing and commits nothing. For each issue of a merged spec it collects, with `null` for what does not exist (never invented): the spec PR and who merged it (gate or human by the gate's merge marker, or unknown; i.e. Gate 1), the plan comment, the questions comment and whether answers followed, the closing PR (stacked or not, merged by), the `devflow/review` status and the number of review rounds (distinct head SHAs with a verdict marker), the tests in the diff (files, count, matrix rows covered, whether the first commit is a `test(...)` commit), the acceptance comment and the release. It builds one JSON object with a fixed shape, injects it into `skills/report/templates/trace.html` (the `{{TRACE_JSON}}` placeholder in `<script type="application/json" id="data">`, with `</` and `<!--` escaped; nothing else in the template changes) and publishes the page as an artifact (an existing artifact URL is updated in place). Steps without data show grey. It exists for demos: the flow ticket → plan → PR → review → tests → merge → acceptance → release with who acted at each step and a link to the evidence, not slides.

## `/devflow:doctor [--fix]`

`disable-model-invocation: true`. Read-only by default; with `--fix` it changes only what the user confirms item by item. Never merges, force pushes, pushes to or deletes the base or a protected branch. Runs every check even when one fails; without a config only checks 3, 8 and 9 run.

1. **Config**: parses and validates against the schema; `devflowVersion` with a lower major or minor version, or missing → warn (a lower patch version only is ok), suggest `/devflow:init --upgrade`.
2. **Templates**: drifted installed templates (same comparison as `--upgrade`); report only.
3. **GitHub access**: MCP reachable (fail otherwise); `gh` missing is a warn (runs stop when the MCP connection drops).
4. **Worktrees** under `worktree.dir`: clean or dirty, branch pushed or not. `--fix` removes clean ones whose branch is pushed or merged (no `--force`), never a dirty one.
5. **Branches** matching `branchPattern` whose PR is merged or closed. `--fix` deletes local ones (`-d`; `-D` only for a merged PR, after a yes); remote ones only after a yes per branch, never the base, a protected branch or a branch with an open PR.
6. **Claims**: in-progress issues with no running session, no open PR and a claim older than 2 hours, and claim comments on issues that are not in progress. `--fix` deletes the comment and swaps in-progress for ready, per item.
7. **Open PRs** labelled `devflow` that are behind, conflicting or red: reported with `/devflow:sync #<pr>`, never fixed here.
8. **Allow-list** in `.claude/settings.json` for background sessions (`bin/devflow-setup allow`): missing rules listed; `--fix` merges them in, never a deny rule or a rule that allows merging or pushing to a protected branch.
9. **Owned by the plugin now** (`bin/devflow-setup leftovers`): `.claude/hooks/block_git_add_all.py` and its test, the settings hook that runs it, a `hook-test` style `checks` entry, deny rules the guard enforces, a maintenance `.claude/loop.md`, a project `.claude/agents/code-reviewer.md`. Each is a `warn` with what replaces it; doctor never deletes them, also not with `--fix`.

Output: a table check → `ok` / `warn` / `fail` → what to do, a line per fix applied or declined, and the one command to run next.

## Risk and the merge gate

Risk flows: spec task (`risk` + reason, approved at Gate 1) → issue label and `Risk:` line → engine (escalate to high on `risk.highPaths`; unlabelled = high) → PR label and body line → gate (acts only on `risk:low`).

**Merge gate** = `.github/workflows/devflow-merge-gate.yml` + `.github/scripts/devflow-merge-gate.cjs`, installed by `/devflow:init`. It exists because target repos may be private on GitHub Free. Runs on `workflow_run` completion (CI workflows and "Claude Code Review"), `status`, and manual `workflow_dispatch` (optional PR number). The workflow lives on the default branch (those triggers only run from there) and uses `DEVFLOW_GATE_TOKEN`, a fine-grained PAT (Contents + Pull requests read/write, this repo only), because pushes and merges made with `GITHUB_TOKEN` do not trigger CI. Config is read from `.claude/devflow.json` at `baseBranch`. It does nothing unless `mergeGate.enabled`; with `dryRun` (default) it only reports.

Per run it walks open PRs labelled `labels.devflow` in priority order (`priorityRank` of the linked issues' labels, the best one when several; the PR's own labels when it links none; then PR number) and **merges at most one**. Priority changes only the order: every rule below still applies. Rules in order; the first failure decides:

1. not a draft; not `risk:high`; has `risk:low`; not `labels.blocked`;
2. base is `baseBranch` (a stacked PR waits for its parent);
3. none of the PR's files (new or, for a rename, previous name) matches `risk.highPaths` or the built-in `.github/**` and `.claude/**`: the label is a claim set by an agent, the file list is re-read on every run. A match skips the PR and relabels it `risk:high` (dry run: `would skip`, nothing changed). This runs before any update-branch, so a high-path PR is never touched;
4. mergeable (not yet computed → skip; conflicts → label the PR and its linked issues blocked, comment once pointing at `/devflow:sync`);
5. not behind its base; if behind, `update-branch` and stop for this PR (CI re-runs);
6. every `mergeGate.requiredChecks` entry is green on the head SHA (check run or commit status; a `devflow/review` commit status counts only when `github-actions[bot]` created it);
7. no unanswered review thread (unresolved, not outdated, last comment not by the PR author).

Then: merge with `mergeGate.method` (merge commit) pinned to the head SHA, retarget open PRs based on the merged branch to `baseBranch`, delete the head branch (same-repo, not a protected name). The run summary lists every PR with action and reason. `tests/merge-gate.test.cjs` covers each rule against a fake Octokit.

**Review check** = `claude-code-review.yml`: sets `devflow/review` pending, reviews with Opus (correctness, tests incl. Test cases rows, scope, CLAUDE.md, and as critical: weakened checks and out-of-scope items that contradict the acceptance criteria), ends its summary comment with a hidden marker `<!-- devflow-verdict {sha, verdict, critical, warning} -->` and publishes `devflow/review` from the bot's latest marker: success only for `pass` on the current head SHA, failure for changes, a missing marker or another SHA. (A verdict file was dropped: Claude Code read the absolute-path Write rule as project-relative and the write was denied.) It runs on open, ready, reopen and every push. If the only commits since the last bot-published result are clean base merges (two parents, made by GitHub's web-flow), it copies that result to the new head instead of re-reviewing, but only when it is a real verdict (success, or a failure described as "N critical, M warning") and the commits since do not change `.github/workflows/claude-code-review.yml`; anything else (e.g. "No verdict ...") is reviewed again. Concurrent runs for one PR are cancelled. The `devflow/review` status is created with `GITHUB_TOKEN` and does not fire `status` events, which is why the gate also listens for the review workflow's `workflow_run`.

## Guard hook (`hooks/guard.py`)

PreToolUse, matcher `Bash|mcp__.*(merge_pull_request|push_files|create_or_update_file|delete_file)`. Exit 2 with a reason on stderr to block:

- any MCP tool whose name ends with `merge_pull_request`;
- MCP tools ending with `push_files`, `create_or_update_file` or `delete_file` when `tool_input.branch` is protected (globs included) or missing/empty (the API then writes to the default branch);
- Bash: `gh pr merge`, `gh api ... /merge` (PUT; an explicit GET is allowed), the GraphQL merge mutations (`mergePullRequest`, `enablePullRequestAutoMerge`), `git push` that targets a protected branch (explicit refspec `:main`, `HEAD:main`, `main`, or pushing while the current branch is protected), `git push --force`/`-f`/`+refspec` (allow `--force-with-lease`), `git push --mirror`/`--all`/`--delete` of a protected branch;
- Bash, git commands that discard work: `reset --hard`, `clean` with `-f`/`--force` in any flag group, `branch -D` (or `-d` with `-f`), `checkout .` / `checkout -- .` (also `./`, `:/`), `restore .` (unless only `--staged`, which just unstages), `stash drop` / `stash clear`, `filter-branch`, `update-ref -d`, `reflog expire`. The message tells Claude to ask the user to run it themselves;
- Bash, skipping hooks: `git commit` with `--no-verify` or `-n` (also in a flag group such as `-nm`; values like `-m "-n"` are not flags) and `git push --no-verify`; `git push -n` is a dry run and stays allowed. `git checkout -f/--force` and `git switch -f/--force/--discard-changes` discard local changes; `git clean` with `-n`/`--dry-run` is a dry run and is allowed even with `-f`;
- Bash, `gh api` writes (explicit non-GET, or `-f`/`-F`/`--field`/`--raw-field`/`--input`) to `git/refs/heads/<protected>` or `.../statuses/<sha>` (forging `devflow/review`); `gh pr edit` / `gh issue edit` removing `labels.riskHigh` (a risk downgrade is a human decision; adding `risk:low` stays allowed because the workflows' gh fallback does it);
- Bash, staging everything: `git add -A`, `--all`, `.`, `./`, `:/`, `*`, `-- .`, combined flags such as `-vA`. `git add -u` stays allowed: it stages only tracked files (how a merge resolution or a rename is staged) and never picks up untracked files. This replaces the per-project `block_git_add_all.py` hook (its cases are in `test_guard.py`).

Global git options before the subcommand (`-C <dir>`, `-c k=v`, `--git-dir=...`, `--no-pager`) are skipped. A wrapper (`sudo`, `env`, `xargs`, ...) is looked through by trying every later `git` / shell token as the start of the wrapped command, so `sudo -u git git add .` is caught without knowing each wrapper's options.

Protected branches = `protectedBranches` + `baseBranch` from `.claude/devflow.json` in the project (`$CLAUDE_PROJECT_DIR`), defaulting to `main`, `master`, `develop` when the file is missing. Parse commands with `shlex` like the TaskBoard `block_git_add_all.py` hook (look through `env`/`sudo`/`bash -c` wrappers; regex fallback when shlex fails). Stdlib only, Python 3.9. Fail closed: any unexpected exception (including unparsable stdin) exits 2 with an "internal error" reason, because any other non-zero exit is a non-blocking error; `/devflow:doctor` check 10 runs the hook to prove it works on the machine. Ship `test_guard.py` (unittest) covering blocked and allowed cases, including that `update_pull_request` and `update_pull_request_branch` stay allowed (`/devflow:sync` needs them). The merge gate Action is outside the hook's reach by design: it is the one place merges happen, and it runs with its own token.

## Formatter and session start hooks

- `hooks/formatter.py`, PostToolUse, matcher `Write|Edit|MultiEdit|NotebookEdit`. Reads `format` (glob to command) from `.claude/devflow.json`; a glob without `/` matches the file name anywhere, one with `/` the path from the project root (`**` crosses directories; no brace expansion). `{file}` is the shell-quoted relative path (appended when absent). Every matching command runs from the project root with a 30 s timeout, output discarded. No config, no key, a file outside the project, a missing binary, a failure or a timeout: exit 0 and nothing printed. It formats; it never decides whether an edit is allowed.
- `hooks/session_start.py`, SessionStart. With a parseable `.claude/devflow.json` it prints `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": <rules>}}` on stdout (stderr would not reach the context): the branch pattern and base, the commit scope with an example, failing test first, stage by name, never edit acceptance criteria or weaken checks, ask on ambiguity, never merge or push to the protected branches, file bugs as `needs-triage`, and the checks. Without one: silent, exit 0.

## Reviewer agent

`agents/reviewer.md` (`devflow:reviewer`, Opus, tools Read/Grep/Glob/Bash, read-only). It carries the review order (correctness, tests, scope, CLAUDE.md, out of scope against the criteria, weakened checks, fix PR fields) and the severity rules. The engine's Review stage passes `agentType: nextTask.reviewerAgent` with its schema; if that type cannot be started it notes it once and uses the default agent for the rest of the run. Users can run it locally on a branch.

## Reusable workflows

`.github/workflows/devflow-review.yml` and `devflow-merge-gate.yml` in this repository run on `workflow_call`. The review's jobs are kept byte-identical to the copy template (`tests/reusable.test.cjs`); the caller holds the trigger, the concurrency group, the permissions and the secrets, passed by name (`CLAUDE_CODE_OAUTH_TOKEN`; `DEVFLOW_GATE_TOKEN` and the optional `DEVFLOW_READ_TOKEN`), because `secrets: inherit` is only guaranteed inside one organization or enterprise and these repositories are user-owned. The gate checks out the caller (for `.claude/devflow.json`) and, sparsely, this repository at the `devflow-ref` input into `.devflow-plugin`, and runs the same gate script, so the logic is not copied into projects. Callers in `skills/init/templates/github/callers/` keep the names the gate needs (`Claude Code Review`) and pin both `uses:` and `devflow-ref` to `{{DEVFLOW_REF}}`. Release tags (`vX.Y.Z`, made by a human) are what callers pin to.
