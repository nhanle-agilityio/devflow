# devflow — design

A Claude Code plugin (3.1.0; `version` in `plugin.json` and `marketplace.json`, history in `CHANGELOG.md`) with eleven project-agnostic commands, plus `/devflow:init` (and `init --upgrade`) for setup:

1. **`/devflow:spec`** — idea → analyse → grill-me → QA matrix → epic issue + one sub-issue per task (risk per task; the human sets readiness or approves the epic). With `--file`: spec PR (risk per task) → Gate 1 (human merges; this approves the risk levels) → GitHub issues labelled ready and `risk:low|high`.
2. **`/devflow:next-task`** — pick up to N ready issues → claim → branch → plan on the issue → implement (QA and dev agents in parallel when the plan allows it, else test first) → checks → verify → review → open PR labelled with its risk, stacked on a parent PR when needed. Runs in the user's checkout, or in its own worktree with `--isolated`; `--chain` runs a lane.
3. **`/devflow:dispatch`** — split the ready issues into non-colliding lanes and start one background session per lane. Use `--plan` to preview the lanes and auto-ready sweep.
4. **`/devflow:sync`** — keep those PRs mergeable: retarget, update behind branches, resolve conflicts, address review threads.
5. **`/devflow:answer`** — answer the questions that blocked an issue; append them to the issue's `## Decisions`, its epic's and (with a spec path, via a PR) the spec's; set it ready again.
6. **`/devflow:accept`** — after merge, check the shipped behaviour against spec or epic criteria. Use merged PR evidence when live verification is unavailable. Gaps become issues.
7. **`/devflow:release`** — merged devflow PRs → semver version → grouped notes with a risk section → GitHub release (draft by default).
8. **`/devflow:report`** — demo-ready trace page of one spec or epic, from GitHub data.
9. **`/devflow:doctor`** — health check of the setup; `--fix` repairs what the user confirms.
10. **`/devflow:approve`** — approve an epic and ready its eligible sub-issues.
11. **`/devflow:autopilot`** — run an approved epic to completion in a self-paced loop.

Merging is done by a human, or for `risk:low` PRs by the merge gate GitHub Action (`devflow-merge-gate.yml`). Claude never merges.

Nothing in the plugin knows about a specific stack. Project mechanics live in `.claude/devflow.json`; project rules (architecture, conventions, "Never" list) live in the project's `CLAUDE.md`. Skills read both and never restate them.

## Principles

- **Deterministic where it matters.** The loop and the order of stages in `next-task` are a Workflow script (`workflows/next-task-engine.js`), not prose. Safety rules are hooks, not instructions.
- **Claude never merges.** The plugin opens PRs and pushes its own feature branches, never merges, never pushes to the base branch, never force-pushes (except `--force-with-lease` on its own branch). Who merges is decided by risk: a human for `risk:high` and unlabelled PRs; the merge gate Action (outside Claude, own token) for `risk:low` PRs once its checks are green.
- **Risk is judged early and enforced late.** The spec judges each task against `risk.highWhen` / `risk.highPaths` (unsure → high) and the human approves the levels by setting the ready label on a sub-issue, approving an epic with auto-ready enabled, or at Gate 1 (`--file`). The engine only ever escalates to high, deterministically, when changed files match `risk.highPaths`. A missing label counts as high.
- **No reliance on GitHub paid features.** Target repos may be private on GitHub Free: no branch protection, no required checks, no native auto-merge. The merge gate is a plain Action that does the checking itself.
- **Model tiers.** Opus handles planning and defaults to reviewing issues with high or unknown risk. Sonnet defaults to reviewing low-risk issues and writes the per-issue plan, implements and ships. Haiku runs mechanical steps such as selecting, claiming, branching, running checks and cleaning up blocked issues.
- **GitHub via the GitHub MCP server** (issues, labels, PRs, comments). `gh` is optional, never required. Adding a missing label to an issue creates it.
- **Merged state comes from one PR read or from git, never from a list.** The GitHub MCP list and search tools report `merged: false` for merged PRs, so every skill and the engine treat a PR as merged only when `pull_request_read` (method `get`) returns a non-null `merged_at`, or `git merge-base --is-ancestor <head sha> <remote>/<baseBranch>` succeeds after a fetch. Gate merges are told from human merges by the gate's marker comment or commit trailer; without that evidence a PR body with a `devflow-run` marker means a human merged it, and only a PR without either falls back to the 3.0.0 rule (a user other than the gate token owner is `human`, else `unknown`). `/devflow:report` also reads the PR's `## Review` section when there is no `devflow/review` status ("local review: pass, N round(s)"), shows Plan and Verify as "skipped (short path)" in a neutral style on the short path, and greys missing steps on the full path.
- **Stack-agnostic verification.** `http` (API calls against the dev server), `browser` (Playwright MCP, or Claude in Chrome if that is what the user has) and `none`. A project enables any subset.
- **All committed content is English.** No `Co-Authored-By` or AI attribution in commits or PRs, unless the project's CLAUDE.md says otherwise.
- **Never write the review bot's at-sign handle into issues, PRs, comments or replies.** Repos that use `anthropics/claude-code-action` start a job on it. No stage posts a re-review trigger: pushing commits re-runs the review (`synchronize`). The handle appears only in the `claude.yml` template, as its trigger.

## Config: `.claude/devflow.json`

```jsonc
{
  "$schema": "./devflow.schema.json",            // optional; init copies the schema next to it
  "github": { "owner": "acme", "repo": "shop", "remote": "origin" },  // remote = git remote that points at GitHub
  "baseBranch": "main",                         // branches start from <remote>/<baseBranch>; PRs target it
  "protectedBranches": ["main", "develop"],     // guard blocks pushes to these and to baseBranch
  "branchPattern": "{type}/{issue}-{slug}",     // type ∈ feat|fix|chore|docs|refactor|test; slug ≤ 5 words kebab
  "commitScope": "#{issue}",                    // Conventional Commits scope, e.g. feat(#12): ...
  "specDir": "docs/specs",
  "labels": {
    "epicApproved": "epic:approved",              // human approval of epic sub-issues for auto-ready
    "ready": "agent:ready", "inProgress": "agent:in-progress", "review": "agent:review",
    "blocked": "agent:blocked", "e2e": "needs-e2e",
    "devflow": "devflow",                       // on every PR devflow opens
    "riskLow": "risk:low", "riskHigh": "risk:high",  // on issues (from the spec) and PRs
    "stacked": "stacked",                       // PR based on another open devflow PR
    "triage": "needs-triage",                   // bugs and gaps nobody triaged; never picked, a human sets ready
    "priority": ["priority:critical", "priority:high", "priority:normal", "priority:low"]  // highest first; no label = normal
  },
  "risk": {                                      // unsure means high
    "highWhen": ["authentication or permissions", "data migration or deleting stored data",
                 "a change to a public API contract that breaks existing clients",
                 "security-sensitive input handling", "payments or money"],
    "highPaths": []                              // globs (** * ?); a PR touching one is escalated to high
  },
  "mergeGate": { "enabled": false, "dryRun": true, "requiredChecks": ["devflow/review"], "method": "merge" },
  "review": { "github": false },                 // true: the GitHub review workflow runs (status devflow/review); false: it skips
  "testing": { "e2eFramework": false },          // false: e2e must rows are covered by Verify, not committed tests
  "checks": [                                    // run in order; all must pass before review
    { "name": "test", "run": "npm test" },
    { "name": "lint", "run": "npm run lint", "timeoutSeconds": 600 }
  ],
  "format": { "*.ts": "npx prettier -w {file}" }, // formatter hook: glob -> command after each edit; quiet, never fails
  "verify": {
    "modes": ["http", "browser"],                // subset of http | browser; [] = none
    "devServer": { "run": "npm run dev", "url": "http://localhost:3000", "readyTimeoutSec": 60 },
    "browserTool": "playwright",                 // playwright | chrome
    "lock": true                                 // one session per machine runs Verify at a time
  },
  "spec": { "testMatrix": true, "qaModel": "opus", "autoReady": "off" }, // QA step of /devflow:spec; qaModel = opus | sonnet
  "nextTask": { "defaultLimit": 3, "maxFixRounds": 2, "maxReviewRounds": 2, "reviewModel": { "low": "sonnet", "high": "opus" }, "maxAgentCalls": 0, "parallelQa": true, "onQuestion": "decide", "trustDecisions": false },  // onQuestion: decide|block, see Decide or block; trustDecisions: the merge gate may merge decisions:review PRs; parallelQa: QA agent writes the acceptance tests in parallel with the dev agent
  "worktree": { "dir": ".claude/worktrees", "setup": [] },  // isolated runs: dir holds the worktrees (keep it in .gitignore); setup commands run once in a fresh worktree
  "dispatch": { "maxLanes": 3, "ignoreHotspots": ["README.md", "CHANGELOG.md"] },  // /devflow:dispatch; optional pluginDir is passed as --plugin-dir to background sessions; ignoreHotspots (paths or * / ** globs) do not join lanes; the fragment directory never needs a lane, so list `<fragmentsDir>/**` there when `changelog.fragmentsDir` is set
  "changelog": { "fragmentsDir": "changelog.d", "file": "CHANGELOG.md" },  // optional; fragmentsDir has no default (unset = off, devflow-changelog exits 2); file defaults to CHANGELOG.md
  "devflowVersion": "3.1.0",                     // plugin version the templates came from (init writes it, init --upgrade updates it)
  "notify": { "push": true, "onDone": true, "onBlocked": true, "onHighRisk": true },  // push notification at the end of a next-task run
  "release": { "tagPrefix": "v", "draft": true, "deploy": "", "notesFrom": "prs" },   // /devflow:release
  "accept": { "model": "sonnet", "labels": ["type:gap"] }  // /devflow:accept; labels go on the gap issues
}
```

Missing optional keys take the defaults shown (`nextTask.reviewerAgent` defaults to `devflow:reviewer`). `github`, `baseBranch` and `checks` are required. `/devflow:init` writes only the keys whose value differs from the schema default (`bin/devflow-setup minimal`; required keys, `$schema` and `devflowVersion` always stay), so a project's file shows what it changed.

`nextTask.reviewModel` defaults to Sonnet for low-risk issues and Opus for high or unknown risk. Each key can be overridden independently. `nextTask.maxAgentCalls` defaults to 0 (unlimited). A positive limit blocks an issue as soon as its agent calls reach the limit, with the reason `agent budget exceeded (<n> calls)`. Each issue starts with a fresh count, and cleanup calls are exempt. A budgeted agent call that returns null or undefined is retried once with the same prompt and options. The retry counts toward the limit. A second empty result uses the stage’s existing failure handling when the budget permits.

## `/devflow:init`

`disable-model-invocation: true`. Sets a project up once; idempotent (re-running shows a diff of proposed changes).

1. Read the repo: git remotes (find the GitHub one), default/current branches, `package.json` scripts, `Makefile`, `pyproject.toml`, lockfiles, framework config, `CLAUDE.md`, existing `.github/workflows`.
2. Propose a filled `.claude/devflow.json` (explain each detected value and where it came from). Ask the user to confirm or edit with AskUserQuestion for anything ambiguous (which remote, base branch, dev server command, verify modes). Write it plus `devflow.schema.json`.
3. Check the CLAUDE.md has what the workflows rely on (conventions, test approach, "Never" list). List gaps; offer to draft additions, never edit CLAUDE.md without a yes.
4. Risk and merge gate (AskUserQuestion, recommended option each time): `risk.highWhen` (show defaults), `risk.highPaths` (globs for auth, migrations, payments, CI config), `mergeGate.enabled` (default false, `dryRun` true), `mergeGate.requiredChecks` (job names found in `.github/workflows/*` plus `devflow/review`), `testing.e2eFramework` (true only when an automated e2e setup exists; say which signal), `spec.testMatrix` / `spec.qaModel`, `worktree.setup` (proposed from the detected tooling; `worktree.dir` stays `.claude/worktrees` unless the user wants another place), `dispatch.maxLanes`.
5. Install mode for the review check and the merge gate (one question): **reusable** (recommended), thin callers from `templates/github/callers/` that `uses:` this repository's `devflow-review.yml` / `devflow-merge-gate.yml` (`on: workflow_call`) at the tag `v<plugin version>` (`{{DEVFLOW_REF}}` replaced; the tag must exist); or **copy** (fallback), the full workflows plus `devflow-merge-gate.cjs`. A private devflow repository must allow Actions access from the user's repositories (Settings > Actions > General > Access), and its gate needs `DEVFLOW_READ_TOKEN` to read the script. Then offer (each a separate yes) the review, the gate (filling the `workflow_run` workflow list with the project's CI workflow names) and `claude.yml` (always a copy) when absent (otherwise show a diff). Tell the user the setup each needs (secrets `CLAUDE_CODE_OAUTH_TOKEN`, `DEVFLOW_GATE_TOKEN`; allow merge commits; gate on the default branch; see the README checklist). Add the worktree dir to `.gitignore` (diff, then a yes). Background sessions cannot answer permission prompts and a plugin cannot grant permissions, so init probes each connected GitHub MCP server by getting the authenticated user (one answers: its tool prefix is used; several: ask the user which; none, an auth error included: stop and tell the user to connect one; a different GitHub MCP prefix already allowed is replaced, shown in the diff), then generates the allow list with `bin/devflow-setup allow` from `checks`, `verify`, `worktree.setup` and the remote (specific prefixes only: no bare interpreter, shell, runner or wrapper rule; runners keep flags and tool up to the first path or glob, a concrete script operand stays; inline-code flags and wrappers give no rule and are returned in `manual`; `curl` is scoped to `verify.devServer.url`'s origin when set), merges it into `.claude/settings.json` after a diff and a yes, and writes no deny rules (the guard covers merging, force pushes, protected branches, destructive git and `git add -A`).
6. Remind the user what the plugin hooks do and that `/devflow:doctor` lists project copies the plugin now owns.

The config is written with `devflowVersion` = the installed plugin version. The newer keys (`dispatch.ignoreHotspots`, `scan.ignore`, `verify.lock`, `notify`, `release`, `accept`) are mentioned with their defaults; only `notify.push` is asked.

**Init and `review.github`.** Init asks `review.github` (AskUserQuestion, `false` recommended; trade-off: no independent party confirms the local review, a hand-opened PR gets no review) and proposes `devflow/review` in `mergeGate.requiredChecks` only when it is true. When `mergeGate.enabled` is true and the effective required list is empty (whatever `review.github` is), init and doctor check 1 warn that the gate will refuse to merge and list the `name:` of each workflow in `.github/workflows/` as candidates. `--upgrade` lists `review.github: true` as one plan item when `.github/workflows/claude-code-review.yml` exists, written only after a yes.

**`/devflow:init --upgrade`.** For a project that already ran init (clean tree, config present). Reads the plugin version and the project's `devflowVersion`; compares byte for byte every installed template (the three workflows, `devflow-merge-gate.cjs`, `devflow.schema.json`, which upgrade keeps managing; a reusable caller is compared with `callers/` at the new tag, so upgrading moves the tag; templates never installed are skipped) and lists the drifted ones and the config keys missing from the project. Because devflow cannot tell whether the project edited a file after install, every drifted file gets a diff and its own yes; a declined file stays. The gate workflow's `workflow_run` list is kept. After the yes: branch `chore/devflow-upgrade-<version>`, copy the accepted files, set `devflowVersion`, validate the config against the new schema, commit `chore(devflow): upgrade templates to devflow <version>`, push, open a PR labelled `devflow` + `risk:high` (it touches `.github/**` and `.claude/**`, so a human merges; a compare link if PR creation fails). Never merges, never pushes to the base.

## `/devflow:spec <idea or path to a brief> [--file]`

`disable-model-invocation: true`. Designed to run in a cloud session (claude.ai/code) on the repo, works locally too. Steps 1 and 2 are shared; then one of two modes.

**Epic mode (default).** No spec file and no PR. After analyse, grill and the QA matrix: build the bodies of the epic (`templates/epic.md`: Goal, Design, `## Decisions`, Tasks table with risk and depends-on) and of one sub-issue per task (`templates/issue.md`, Context line `Epic: #<epic>`), with issue numbers filled at their widest expected width, and measure each by JavaScript string `length`; if one exceeds 65,000 characters nothing is created and the user is told to use `--file`. Then search by exact title (trimmed, case-sensitive, open or closed) and reuse matches without editing them (except a reused epic's Tasks table, filled with the issue numbers); create the epic `[<slug>] <title>` labelled `type:epic` only, then the sub-issues `[<slug>] T<n>: <title>` in dependency order, labelled risk (`labels.riskLow` or `labels.riskHigh`), `labels.e2e` when needed and `type:<type>`, never the ready label. Link each sub-issue with `sub_issue_write` (method `add`, existing links skipped; a failed link is reported and does not stop the run) and write the issue numbers into the epic's Tasks table. The human can set `labels.ready` on each approved sub-issue or approve the epic for auto-readying. A task requiring a human step first gets a `Ready: manual` line and the instruction in Context.

**`--file` mode.** The steps of 2.9.0, each announced with its number (the spec link replaces the `Epic:` line in the issues, which carry `labels.ready` except when a human step must happen first):

1. **Analyse.** Read `.claude/devflow.json`, `CLAUDE.md`, and the code the idea touches. Produce a short analysis: current behaviour, affected areas (backend/frontend/infra/data), risks, unknowns. Do not write files yet.
2. **Grill.** Invoke the `grill-me` skill on the idea plus the analysis. Keep going until every unknown is decided or explicitly deferred. If `grill-me` is not available, run the same interview inline: one question at a time, each with a recommended answer.
3. **Spec + tasks.** Create branch `spec/<slug>` from `<remote>/<baseBranch>`. Write `<specDir>/<YYYY-MM-DD>-<slug>.md` from `templates/spec.md`: problem, goals/non-goals, decisions (with the grill answers), design (API contracts, data model, UI screens and states, mocks if any — mocks go in `<specDir>/<slug>/`), risks, and the **task list**. Each task: stable id `T1..Tn`, title, type, `area`, depends-on, acceptance criteria written as checkable behaviour (API: request → response; UI: user action → visible result), files/areas in scope, test plan, `needs-e2e` yes/no, size S/M (split anything bigger), **risk** `low|high` with a one-line reason (judged against `risk.highWhen` and `risk.highPaths`; unsure → high), and **hotspot files** other tasks are likely to touch (`/devflow:dispatch` uses them to plan lanes).
4. **Test matrix (QA).** Skipped when `spec.testMatrix` is false. A QA agent (Agent tool, model `spec.qaModel`, default opus) gets only the spec file and `CLAUDE.md`, not the grill conversation, so it tests what the spec says rather than what was meant. It returns test-case rows (id `T<n>.<k>`, criterion, case happy/error/edge/boundary, Given/When/Then, level unit/integration/http/e2e, priority must/should; every criterion has a must row), the criteria it cannot test as written, and cases the spec leaves undecided. Those go back to the user one at a time with a recommended answer; the spec is updated and QA runs again, at most 2 rounds, leftovers under Risks. The rows go into the spec's Test matrix and each task's test plan points at them. Opus is the default because the value of the step is in spotting what the spec does not say, and the matrix is copied into every issue, so a miss repeats; it runs once per spec, so the cost is small.
5. **Spec review.** Runs in both modes after QA and before any issue is created or the spec PR is opened. A fresh general-purpose agent (model `spec.qaModel`, default opus, no new config key) gets only the user's brief and the path of the draft or spec file. It reports missing requirements, contradictions and tasks that are not independent, each critical, warning or suggestion. It differs from the QA step: QA writes the test rows and lists untestable criteria and missing cases; the spec review checks the draft against the brief only and does not judge testability. Only critical findings start a round (fix, review again); at most 2 reviewer calls in total, after which the remaining critical findings go to the user, who proceeds or stops. Warnings and suggestions are shown once. Open questions: the grill continues until none is open; issues (or the spec PR) wait while one is open unless the user defers it, and a deferred question goes into an `## Open questions` section of each affected sub-issue (in `--file` mode also into the spec's Risks and unknowns, and the issues created after the merge get it too).
6. **Spec PR.** Commit `docs(spec): <title>`, push the branch, open a PR to `baseBranch` titled `spec: <title>`, body = summary + task table (incl. risk and reason) + test matrix size and QA questions resolved/open. No need to ask before pushing the spec branch or opening the PR.
7. **Gate 1.** Ask exactly one question (AskUserQuestion): "Spec PR <url> merged? Merging also approves the risk levels in its table." — options: merged / changes requested / abandon. Changes requested → read the PR review comments, update the spec on the same branch, push, ask again. Abandon → close nothing, stop. Merged → verify through MCP that the PR is merged; if not, say so and ask again.
8. **Issues.** Search existing issues for each task title first (no duplicates; re-running after a partial failure must be safe). Create one issue per task from `templates/issue.md`: title `[<slug>] T<n>: <task title>`, body with spec link (on baseBranch), acceptance criteria as a checklist, scope, test cases (the task's Test matrix rows, or the test plan when there is no matrix), `Depends on #<n>` lines (resolve task ids to issue numbers — create in dependency order), a Risk line and Hotspots section, labels `labels.ready` plus `labels.riskLow` or `labels.riskHigh` plus `labels.e2e` when needed plus `type:<type>`. Then comment on the spec PR with the issue list. Final message: table task → issue.

## `/devflow:next-task [limit | #issue ...] [--isolated] [--chain]`

`disable-model-invocation: true`. Entry point only; the work is the workflow.

Preflight (inline, fail fast with a clear message):
- `.claude/devflow.json` exists and parses; else tell the user to run `/devflow:init`.
- Working tree clean. Not isolated: current branch noted (restored after every issue; detached HEAD is refused). Isolated: a detached HEAD is fine, no start branch.
- `git fetch <remote> <baseBranch>` succeeds.
- GitHub MCP reachable (get the authenticated user).
- Run `${CLAUDE_PLUGIN_ROOT}/bin/devflow-gh` and pass its JSON `gh` value as `ghCli`.

Flags: `--isolated` (own worktree) and `--chain` (the explicit issues are a lane: in the given order, each stacked on the previous one; needs explicit issues).

**Isolated setup** (before the workflow). Inside a linked worktree already (`git rev-parse --git-dir` ≠ `--git-common-dir`): use it. Otherwise `name` = `issue-<n>` or `lane-<n1>-<n2>...`; `git fetch <remote> <baseBranch>`; `git worktree add --detach <worktree.dir>/<name> <remote>/<baseBranch>` (an existing worktree at that path is reused only when clean); the EnterWorktree tool with that path (if unavailable: stop, tell the user to start with `claude -w`). Then run each `worktree.setup` command in order; a failure stops the run. The worktree is created by devflow, not left to background auto-isolation (see Verified behaviour).

**`claimId`**: `<timestamp>-<name>-<pid><random>` (`main` as name when not isolated); the pid and random suffix separate two sessions started in the same second on the same issue.

Then call the Workflow tool with name `devflow:next-task-engine` and `args = { config: <parsed devflow.json>, limit: <n or config default>, issues: [<explicit issue numbers>], startBranch: <current branch, "" when isolated>, prTemplatePath, isolated, chain, claimId, ghCli }`. `prTemplatePath` points at `templates/pr.md`; `bugTemplatePath` at `skills/spec/templates/bug.md`. When it returns: isolated and the worktree is clean with every created branch pushed → ExitWorktree and `git worktree remove <path>`; otherwise ExitWorktree and keep it, telling the user the path and why. Print the summary table from the result fields only: issue → PR (risk, and the PRs it is stacked on) / blocked (reason) / skipped (reason, including `already claimed` / `claimed by <id>`), plus a Notes column with the entry's `notes` joined by "; " verbatim. The Next column comes from the engine too. It shows the answer or sync command, a prompt to merge by hand, “nothing”, or “check by hand”. For a PR, failing checks take precedence over sync for conflicts or a behind branch. A high-risk or untrusted `decisions:review` PR then waits for a human. If an entry says "GitHub MCP unavailable", say the run stopped there and `/devflow:doctor --fix` cleans up once GitHub is back. Merge eligibility follows the gate rules below.

**Notify** (last step, after the table). When `notify.push` is true and the PushNotification tool exists (else skip silently), send one message of at most 200 characters naming the repository: blocked issues (`notify.onBlocked`), else a `risk:high` PR waiting for a human (`notify.onHighRisk`), else the done count (`notify.onDone`); several that apply are combined. It is how background lanes are followed from a phone.

## Workflow `next-task-engine.js`

Plain JS, no `Date.now()`/`Math.random()`, no filesystem (the `claimId` therefore comes in as an argument). Within one run, tasks run **sequentially** in one working tree (the main checkout, or the worktree when `isolated`); parallelism is across sessions (see Parallel work). Every agent gets the config in its prompt. Every agent returns structured output (schemas below); a stage that fails marks the issue blocked and moves on to the next issue.

**Notes.** Each result row carries `notes`: facts the engine records as they happen (a lane that continued after an issue that did not ship, a resumed branch, a parent that merged meanwhile, QA tests that did not fail first, manual checks not passing). The skill prints them verbatim; `/devflow:report` and the summary rely on them instead of inferred stories.

**GitHub MCP stop.** Without `gh` (`ghCli` false) the MCP note tells every agent: if the MCP server is unavailable, stop and report starting with "GitHub MCP unavailable". `block()` recognises that marker (also from Claim's `problem`): no cleanup is possible, so it posts nothing, returns the row `blocked` with `mcpDown`, and the main loop skips every remaining issue with that reason. The stopped issue keeps its in-progress label and claim; `/devflow:doctor --fix` clears them.

**Stages read the issue from GitHub.** The Plan, Integrate, Implement, QA, Fix, Verify and Review prompts do not carry the Select copy of the issue body (it can be cut or stale). Each names the title and `#<n>` in `<owner>/<repo>` and tells the agent to read the issue from GitHub and treat it as the source of truth. The Select copy (still the full body) is used only for parsing in the engine: the `Depends on` lines, the Test cases levels (together with Plan's `httpOrE2eRows`), the spec path when Claim returns none, the `Risk:` line, and the acceptance criteria count. All seven stage schemas allow `problem`; one that `mcpDown` recognises stops the run as at Claim. Claim returns `labels`, `specPath` and `introducedBy`; risk, fix-issue detection and the e2e label use them, and a difference from the Select copy is noted (`labels differ from the selection: <labels>`, `spec path differs from the selection: <path>`). Plan returns `httpOrE2eRows` (Verify runs when true) and `acceptanceCriteria`, an integer compared with the number of top-level `- [ ]` / `- [x]` items under the first heading or bold line containing `Acceptance criteria` in the Select copy (up to the next heading or bold line, 0 without one); a difference is logged and noted (`acceptance criteria: plan read <a>, selection had <b>`), a missing or non-integer count is noted (`plan did not report the acceptance criteria count`), and the run continues. **Review** runs on `nextTask.reviewerAgent` (read-only) with `ghCli` true, reading the issue with `gh issue view <n> --repo <owner>/<repo> --json title,body,labels` (the only `gh` rule `devflow-setup allow` emits is `Bash(gh issue view:*)`); the review schema requires `issueRead`. Without `ghCli` the round runs on the default agent with the MCP note (note `review ran on the default agent: gh is not installed`). A reviewer that returns `issueRead: false` or reports "GitHub MCP unavailable" is re-run on the default agent for the same round (note `review ran on the default agent: the reviewer could not read the issue`), later rounds go straight to the default agent, and a default agent with `issueRead: false` blocks the issue at Review (`Review: the review could not read the issue`).

**Short path.** Right after Claim refreshes the labels, `pathFor(issue, config)` decides once: `short` when the labels include `labels.riskLow`, include neither `labels.riskHigh` nor `labels.e2e`, and the issue body has no Test cases row with level `http` or `e2e`; else `full`. On the short path there is no Plan agent (no plan comment, no acceptance-criteria cross-check, no `httpOrE2eRows`), no QA or commit agent (Implement runs the single-agent branch with plan text `none (short path: no plan stage)`, also with `parallelQa`), and the Verify block is skipped: `state.verify` is `skipped (short path)` when Verify would have been needed (`needsVerify`), else `not needed`, and the Ship prompt's Verification line shows it. The spec-read fix, root-cause round, Check, Review (scan + reviewer, `maxReviewRounds`), Risk and Ship are unchanged; a short path issue escalated to `risk:high` by Risk ships as high and Verify never runs after the fact. Every result entry produced after the decision carries `path: short|full`.

Phases: `Select`, then per issue `Implement` (Claim, Branch, Integrate, Plan, Implement, Commit), `Check`, `Verify`, `Review`, `Ship`, then `Report`.

0. **Priority and triage** (deterministic, pure helpers): `priorityRank(labels, labels.priority)` is the index of the first listed label the issue has; no label counts as the entry ending in "normal" (after every entry when there is none). `orderIssues(issues, labels.priority)` orders the selection: dependencies inside the set first (Kahn), ties by effective rank then number, where an issue's effective rank is the best rank of itself and every issue that depends on it, so a critical child pulls its open parents forward; a cycle places the best remaining issue and goes on. A `chain` run keeps its given order. Issues labelled `labels.triage` are skipped in code (reason "needs-triage: a human sets it ready first") as well as in the Select prompt. Nothing is preempted: the order applies to the selection of one run.
1. **Select** (haiku, schema `{issues:[{number,title,labels,body,dependsOn:[int],parents:[{issue,prNumber,branch,inRun}]}], skipped:[{number,reason}]}`): explicit issues if given, otherwise open issues with `labels.ready`, not labelled inProgress/blocked/triage, no open PR referencing them. Exception: an issue whose only open PR is its own `labels.devflow` PR (`Closes #<n>`) and that lacks `labels.review` is kept, with that PR's head branch as `resumeBranch`; the Branch stage then resumes exactly that branch instead of deriving a name from `branchPattern`. Any other open PR still skips it. Dependencies: all `Depends on` issues closed → normal (`parents: []`); every open dependency has an open PR (`inRun: false`) or is selected earlier in this run without a PR yet (`inRun: true`, the engine fills in the PR once the parent ships) → **stacked** on all of them; an open dependency with neither, or an in-run parent that did not ship, skips the issue naming it. Order: parents first, then oldest; with `chain` and explicit issues, exactly the given order (an earlier issue of the same list is a parent only when there is a real `Depends on`; lane stacking is done by the engine). The agent returns up to 3×`limit` candidates; the engine works on `limit` of them (a skipped child does not count). `log()` what was skipped and why (no silent caps).
2. Per issue, in order:
   - **Claim** (haiku, schema `{taken, takenBy?, assignedByRun, lastBlockedAt, claims:[{commentId, claimId, createdAt, author}]}`): a comment-based lock. The issue is taken only when it has an assignee other than the authenticated user, or `labels.inProgress` / `labels.blocked` / `labels.review`; then return `taken` and change nothing (the issue is skipped as `already claimed`). An issue assigned only to the authenticated user with none of those labels is free (a human self-assigned it, or a past run left it). Otherwise add the authenticated user as assignee only when not already assigned and return `assignedByRun` (true only when this call added them; missing counts as false), add `labels.inProgress`, remove `labels.ready`, post `<!-- devflow-claim id=<claimId> -->` + `Claimed by devflow (<claimId>).`, re-read all comments and return every claim comment and the latest `<!-- devflow-blocked -->` comment’s `created_at` (or null). The engine requires our claim to be present. `pickClaimWinner` ignores claims created before the latest block, then takes the earliest `createdAt`, breaking ties by smallest comment id. A losing run uses a haiku agent to delete its own claim comment; labels belong to the winner, and so does the assignee unless `assignedByRun` is true and the winning claim's `author` differs from ours, in which case the loser removes the authenticated user from the assignees (a missing author counts as the same login, nothing removed); the issue is skipped as `claimed by <id>`. No two sessions can both pass, as long as GitHub's `created_at` order is the same for both readers.
   - **Branch** (haiku): the engine fills `branchPattern` using the issue number, the type label or inferred title type, and up to five lowercase ASCII alphanumeric words from the title after stripping a leading task prefix. The agent runs the exact `devflow-run branch` command and returns its JSON. The start ref is the remote base or the single stacked parent. An existing PR head supplied by Select takes precedence. Otherwise, the exact computed name wins. When it is absent, one local or remote branch with the same `<type>/<issue>-` prefix and an issue-scoped own commit is resumed. The engine records its name and the computed name in the run notes and PR assumptions. Several candidates block with a question listing them. A missing single parent triggers a PR read and a retry from the base only if the parent PR merged. An aborted base or single-parent conflict goes to Integrate with its file list. A branch with earlier work skips parallel QA and passes its own commits to Implement. Multistack integration and its checks stay in Integrate.
   - **Plan** (sonnet, after Branch and Integrate, schema `{status: ready|blocked, plan, questions:[string, each starting "[BA] " or "[QA] "], qaFiles:[], devFiles:[], specRead}`): reads the spec (`git show <baseRef>:<path>`; `specRead` required when the issue links one), the acceptance criteria, CLAUDE.md and the touched code. Writes no code. Posts the plan as an issue comment whose first line is `<!-- devflow-plan -->` (edited in place if one exists): Files to change; Tests (a row per Test cases id); Risks; Order of commits; Open questions. `qaFiles` = test files the QA agent owns (the tests for the issue's Test cases rows), `devFiles` = files the dev agent will change; a file in both blocks the issue at Plan ("ownership overlap"). A `## Decisions` section in the issue body overrides the spec where they differ (Plan and Implement prompts). Nobody approves it. `blocked` (BA questions: spec gaps; QA questions: Test cases rows not testable as written) → the issue is blocked at stage Plan before any code, with the merged questions comment (below). Otherwise the plan text is handed to Implement, which follows it and records deviations under `assumptions`.
   - **Implement, single agent** (`parallelQa` false, or no `qaFiles` such as docs-only issues; sonnet, schema `{status: done|blocked, summary, commits:[sha+msg], filesChanged, assumptions:[], outOfScope:[], blockedReason?}`): read the issue and the linked spec; follow CLAUDE.md. For behaviour changes and bug fixes: commit a failing test first (`test(<scope>): ...`), confirm it fails for the right reason, then the implementation (`feat|fix(<scope>): ...`). When the issue has a Test cases table, write a test for every `must` row, traceable to its row id: a naming pattern stated in the issue, spec or plan is followed exactly (no extra prefix; Review flags a mismatch as a warning), otherwise `test_t<task>_<n>_...` or a `# T1.2` comment. The QA agent follows the same rule. With `testing.e2eFramework` false, `e2e` rows get no committed test: Verify covers them. Stage files by name. Stay inside the issue scope; record anything else in `outOfScope`. Ambiguity that changes behaviour and is not answered by the spec → `blocked` with the question (no guessing on contracts); minor ambiguity → decide and record in `assumptions`.
   - **Manual checks** (both Implement variants; schema field `manualChecks:[{rowId, result: pass|fail|not-run, evidence}]`): a Test cases row that cannot be an automated test (a manual or review checklist, e.g. a Makefile target or a README line) is checked by hand (in a scratch directory when it writes files) and reported per row with the command and relevant output. A `must` row may be `not-run` only when it truly cannot run, with the reason. The engine merges them per row (a later check after a fix replaces the earlier one). Review gets them: a `must` row neither tested nor manually passed, and a failing manual check, are warnings. Ship puts them in the PR's Tests section as a table; rows not passing are added to the result notes.
   - **Implement, parallel QA** (`nextTask.parallelQa` true and `qaFiles` non-empty): two sonnet agents run in parallel in the same checkout, neither commits. **QA** (schema `{status: done|blocked, tests:[{rowId, test}], filesChanged, questions:[], specRead}`) writes the acceptance tests for every `must` Test cases row from the spec and the issue only (black box: it never reads the implementation diff) and touches only `qaFiles`. **Dev** (the Implement schema above) writes the implementation and touches no `qaFiles`; it may add extra tests in other files. Their questions are merged (below). The engine then blocks the issue if QA changed a file outside `qaFiles` or dev changed a qaFile.
   - **Commit** (haiku, parallel QA only): the engine builds the input for `devflow-run commit` from the issue title, commit scope, type label, QA and dev file lists, Plan's `separateCommits` decision, test check and worktree setup. The agent runs the command and returns its JSON. Unlisted changes block the stage. The engine formats the commit entries as `<sha> <message>` and maps the red check to `failedFirst` and `failureNote`. Tests that pass at the QA commit are logged and added to the PR assumptions. Commit and Fix prompts carry the CLAUDE.md commit rules and the plan's order of commits. Fix rounds keep QA files reserved for the QA fix agent. A dev fix agent that thinks a QA test is wrong returns a blocked result with a `[QA]` question.
   - **Root cause** (fix issues only; `isFixIssue`: a `type:fix`, `type:bug`, `bug` or `fix` label, an `accept.labels` label, a `Gap:` or `fix:` title, or a body with `## Introduced by`): Implement returns `rootCause {cause, introducedBy, whyMissed}`; when it is missing, one Fix round asks for it, then the PR says "unknown" and the result notes it. That round never blocks the issue (an agent that dies or returns blocked is noted, and the PR ships with "unknown"), except when it edits a QA file. `devflow-run pr-body` fills the Root cause, Introduced by and Why it was missed sections when the PR template has them.
   - **Check** (haiku): run `node "<pluginRoot>/bin/devflow-run" check` and return its JSON. The engine maps failed entries to `{check, output, files?}` using the check name, output tail and attributed repository files. If failed: **Fix** (sonnet) with the failures, then Check again; up to `maxFixRounds`. A failure attributed to a `qaFiles` file goes to the QA fix agent: a Review finding (critical or warning) whose file is in `qaFiles`, or a failing check whose failure the Check stage attributes (`files` on the failure) to a `qaFiles` file, starts a round with the QA fix agent (sonnet, label `qa-fix`, the Implement schema plus optional `positions`), which may edit only `qaFiles` (any other change blocks). The dev Fix agent still never edits `qaFiles`. A round with QA-file and other findings runs the QA fix agent, then the dev Fix agent (always, even when the QA fix agent changed nothing); the dev Fix agent also runs when the QA fix agent returns `test is right` for a finding, so it can take a position on it. QA and dev fix rounds share one counter (`maxFixRounds` for Check, `maxReviewRounds` for Review): a round counts once, also when it changes nothing. When the QA fix agent returns `test is right` and the dev Fix agent returns `code is right` for the same finding, the issue blocks with one `<!-- devflow-questions -->` comment holding both positions (always a block, whatever the question handling); `test is right` without a dev position leaves the finding open for the next round or the round limit. Still failing → blocked.
   - **Verify** (sonnet, schema `{ran, mode, steps:[{action, expected, actual, pass}], notes}`): only if `verify.modes` is non-empty and the issue has `labels.e2e`, the diff touches UI, or the issue's Test cases table has a row with level `http` or `e2e`. Start the dev server in the background, wait until `url` answers (≤ `readyTimeoutSec`), walk every acceptance criterion and every Test cases row with level http or e2e: `http` with curl, `browser` with the configured browser tool (navigate, act, read the page; take screenshots for the agent's own check). Stop the server. With `verify.lock` enabled (the default), the agent runs `devflow-run lock acquire --name verify` before starting the server to reserve the port across linked worktrees. If the lock stays busy it returns `ran=false` with the note "verify lock busy". After stopping the server it always runs `devflow-run lock release --name verify` if it acquired the lock. Failures → one Fix round (sonnet) → Check → Verify again; still failing → blocked.
   - **Weakened-checks scan** (haiku, before every Review round, schema `{scanned, hits, error?}`): runs `node "<pluginRoot>/bin/devflow-scan" <parentRef> .claude/devflow.json` and returns only its output. The script runs `git diff --unified=0 <parentRef>...HEAD` itself and scans it with the engine's pure `scanWeakenedChecks(diff, checkConfigGlobs(checks))` (loaded through the `args.exports` hook, so there is one implementation), so no diff travels through an agent. `parseDiff` reads `--- ` / `+++ ` as file headers only before a file's first `@@`. It finds: added `# noqa`, `type: ignore`, `pyright: ignore` / `pylint: disable`, `pytest.mark.skip|skipif|xfail`, `unittest.skip`, `it|test|describe.skip|only`, `xit` / `fit`, `eslint-disable`, `@ts-ignore|nocheck|expect-error`, empty `except` (one line, or `pass` on the next line), empty `catch {}`, Go `t.Skip|Skipf|SkipNow` (in `_test.go` files), `@Disabled` / `@Ignore`, Rust `#[ignore]`, `//nolint` and `# rubocop:disable`; hollow assertions (`assert True`, `expect(true).toBe(true)`, `assert.ok(true)`) in test files (`src/test/**`, `*Test.java`, `*Tests.java`, `*Test.kt`, `*_spec.rb` and `*_test.rs` count as test files); none of these line patterns run on prose or docs files (`.md`, `.mdx`, `.txt`, `.rst`, `.adoc`, anything under `docs/`); in test files a deleted file, fewer test definitions or fewer assertions than before; and any changed or deleted line that existed before the branch in a test or fixture file (`fixtures/`, `testdata/`, `__snapshots__/`, `*.snap` count as fixtures), `changed-existing-test`, with blank lines, comment-only lines, lines that return unchanged apart from whitespace, added lines, new files and pure renames excluded; a deleted fixture file yields one `changed-existing-test` hit (a deleted test file keeps its single critical `deleted test file` hit), the added-line patterns ignore string literals in non-test source files, and a test file the Plan gives to Dev (`devFiles`) gets no automatic `changed-existing-test` warning (QA files stay guarded). Unlike the other hits it becomes a warning finding (not critical): routed by file like any finding (a `qaFiles` file to the QA fix agent, others to the dev Fix agent), and the reviewer may accept it in `acceptedWeakenings` when a Test cases row names the change. The QA prompt also forbids changing an existing test or fixture no row names (report it in the result instead) and tests that depend on branch state (diff against the base, branch name, unpushed commits, the date); such a row is a review check, not a test. and any edit to a file that configures the checks (`.claude/devflow.json`, Python/JS/Go linter, type checker and test runner configs, `.pre-commit-config.yaml`, `.github/workflows/*`, `**/Makefile` when any simple command of a check (split at `&&`, `||`, `;`, `|`) runs `make`, `.github/scripts/**`, `.github/actions/**`, and script paths named in `checks[].run`). The optional third argument `ignoreGlobs` (config key `scan.ignore`, globs matched with `globToRegExp`, default `[]`; anything but an array means none) skips every matching file with no rule applied (line patterns, deleted test file, removed tests and assertions, check configuration); `bin/devflow-scan` reads it from the config and adds `"ignored": [paths]` to its output only when it skipped a file. `.claude/devflow.json` is exempt from ignoring, so a change that adds a glob to the list is itself a `check configuration changed` hit (and, under `risk.highPaths`, a high-risk path at the merge gate). `package.json` and `conftest.py` are not on the list, since most of their edits are dependencies and fixtures; instead, in any `package.json`, a changed script-like entry (`test`, `lint`, `build`, ... with a non-version value) or the opening of an embedded tool config (`jest`, `eslintConfig`, `scripts`, ...) is one `check configuration changed` hit, and an added `collect_ignore` / `pytest_ignore_collect` is a `collection ignored` hit.
   - **Review** (risk-based model, read-only, schema `{verdict: pass|changes, findings:[{severity: critical|warning|suggestion, category?, file, line, problem, fix}], acceptedWeakenings:[{file, line, reason}]}`): review `git diff <parentRef>...HEAD` (so a stacked PR shows only its own changes) against the issue's acceptance criteria, the spec and CLAUDE.md; correctness first, then tests (does each change have a test that fails without it; a `must` Test cases row without a traceable test is a warning, except `e2e` rows when `testing.e2eFramework` is false), then scope creep, then the out-of-scope list (an item that leaves an acceptance criterion or a `must` row unmet is critical: an AC violation written as "left as is" is in scope), then the scan hits. Every hit is critical unless the reviewer lists it in `acceptedWeakenings` because the issue itself asks for it; the engine adds a critical finding for each hit that is neither reported nor accepted, and a `pass` verdict does not override it. The loop exits on findings only, not on the verdict: it ends when no finding is blocking (the verdict is informational), so `pass` with a warning starts a fix round and `changes` with only suggestions ships; a finding is non-blocking only when its severity is exactly `suggestion`, so any other severity blocks (fail closed). Critical/warning → Fix (sonnet) → Check → Review again, up to `maxReviewRounds`; suggestions go to the PR body, not fixed. A finding with `category: "commit-structure"` (commit split, order or message wording) is a suggestion whatever its severity, decided before routing by file: it is listed under the PR's Review notes and never starts a fix round or a block (`agents/reviewer.md` and the review prompt tell the reviewer to set it). A finding in a `qaFiles` file goes to the QA fix agent: a Review finding (critical or warning) whose file is in `qaFiles`, or a failing check whose failure the Check stage attributes (`files` on the failure) to a `qaFiles` file, starts a round with the QA fix agent (sonnet, label `qa-fix`, the Implement schema plus optional `positions`), which may edit only `qaFiles` (any other change blocks). The dev Fix agent still never edits `qaFiles`. A round with QA-file and other findings runs the QA fix agent, then the dev Fix agent (always, even when the QA fix agent changed nothing); the dev Fix agent also runs when the QA fix agent returns `test is right` for a finding, so it can take a position on it. QA and dev fix rounds share one counter (`maxFixRounds` for Check, `maxReviewRounds` for Review): a round counts once, also when it changes nothing. When the QA fix agent returns `test is right` and the dev Fix agent returns `code is right` for the same finding, the issue blocks with one `<!-- devflow-questions -->` comment holding both positions (always a block, whatever the question handling); `test is right` without a dev position leaves the finding open for the next round or the round limit. A fix that implements an out-of-scope item returns it in `outOfScopeDone` and the engine drops it from the list.
   - **Risk** (deterministic, in the engine, no agent): level = the issue's risk label (`unknown` if none, treated as high); reason = the issue body's `Risk:` line. If any changed file matches a `risk.highPaths` glob, the level becomes high and the reason names the file. Accepted scan hits still in the last reviewed diff, or a scan that could not run (no `pluginRoot`, the agent died, or the script reported `scanned: false`), also make it high, with the hits named in the `Risk:` line and the result notes. So does a required verification that could not run (`ran: false`: lock busy, dev server never started, tool unavailable): the engine still continues, but the first line of the verify notes is named in the `Risk:` line and the result notes, joined with any scan reason by "; ". An escalation also sets `labels.riskHigh` on the issue.
   - **Ship** (sonnet): step 0 looks for an open PR with head `<branch>`; when one exists (left by an earlier run) Ship reuses an open PR for the branch: it runs `devflow-run push`, retargets the base to the intended base when it differs, updates the title and body from `devflow-run pr-body`, adds the computed labels without removing any label already on it (never `risk:high`), opens no new PR, returns `reused: true` and continues with the issue labels; the engine then adds the note `reused open PR #<n>` (status stays `pr`). Otherwise, run the same push and rendering commands and open a PR via MCP with the returned title and body unchanged. The engine builds the renderer payload from the stage results (what, how, risk line, tests, verification evidence, assumptions, out of scope, `Closes #<n>`; when the shipped issue is the last open sub-issue of an epic whose body has a `Resolves: #a, #b` line, one more `Closes #<n>` for each listed issue that is still open, and a note in the body for a number that does not exist or is in another repository). The PR base is `baseBranch`, or the parent PR's branch when stacked (the body then says it retargets when the parent merges). Label the PR `labels.devflow`, `labels.riskLow|riskHigh` and, when stacked, `labels.stacked`; add `labels.review` to the issue and remove `labels.inProgress`. Each remaining out-of-scope item that is a real problem (not a remark) becomes a follow-up issue `[follow-up #<n>] ...` from the bug template (`args.bugTemplatePath`) labelled `labels.triage` (default `needs-triage`, never ready: a human triages it), with a comment suggesting a priority and a risk with reasons, unless an open issue covers it, and is linked in the PR's Out of scope section; its body has a `Found in: #<pr>` line (the branch name when no PR exists yet) and the `file:line` of the problem when one is known; Ship returns them in `followUps` and the engine notes them. Return `{prNumber, url, followUps}`. When stacked on one parent, Ship first re-reads the parent PR: if the gate merged it meanwhile (and deleted its branch), Ship clears the stack line in the payload, targets `baseBranch`, omits the stack label and returns `unstacked`. Epic closures and follow-up links are payload updates as well. When follow-up links become available after PR creation or reuse, Ship renders again and updates the PR with the returned title and body. Branch and Integrate apply the same rule when a parent branch is already gone.
   - **Review trace and run marker at Ship.** The engine supplies the exact lines in the `pr-body` payload. The PR body gets a `## Review` section: `Review: pass after <n> round(s) - local devflow reviewer in this run (GitHub review: off|on)`, `Path: short (Plan and Verify skipped)|full` and `Verify: ran|skipped (short path)|not needed|could not run`, always. It also gets one hidden line `<!-- devflow-run {"path":"short|full","reviewRounds":<n>,"claimedAt":"<ISO>"} -->` (built with JSON.stringify; `claimedAt` is the `createdAt` of this run's winning claim, `null` when unavailable). Each result entry carries `reviewRounds` (review rounds that ran).
   - **Decide or block.** Agents give each question a recommendation, a reason and all ten boolean flags. The pure `classifyQuestion` uses the full branch diff against the parent ref.
     - `block` applies when the mode is `onQuestion: block`, required classifier input is missing or invalid, or the recommendation is irreversible, weakens a check, drops a required test row, requires destructive Git, or goes outside the repository. If any question blocks, the run posts all questions in one `<!-- devflow-questions -->` comment with their recommendations. In that comment, questions that change a criterion keep the typed-answer suffix. Session rules also stop work for missing secrets or credentials and permission problems.
     - `decide-high` applies to an otherwise answerable product decision or a recommendation that changes a criterion, contract or stored format, lowers risk, or has a full-diff file matching `risk.highPaths`. The decision line says “needs human review”. The PR gets `risk:high` and `decisions:review`, the issue is relabelled to high risk, and a human merges even with `nextTask.trustDecisions` enabled.
     - `decide` applies to the remaining answerable questions. For both decide outcomes, the run uses the recommended options, records them in the issue's `## Decisions` and the PR's `## Decisions taken`, and passes them to subsequent agents as answers. The run never edits the issue's acceptance criteria. New decisions add `decisions:review`. Warnings still open after the last review round use the same classifier and appear in the PR when accepted. Critical findings still open block.
     - **Run-error bug.** Checks still red after the last fix round or a missing required environment variable or secret trigger one best-effort cleanup step. It searches open issues for `<!-- devflow-run-error #<issue> -->` and reuses a match. Otherwise it files a bug from the bug template with only `labels.triage`, quoting the failing output and linking the blocked issue. It then comments on the blocked issue with the bug link. The lane continues if filing or linking fails.
   - **Merged questions.** Questions from Plan (BA, QA), from the QA agent and from the dev agent are collected into ONE issue comment whose first line is `<!-- devflow-questions -->`: numbered, each tagged [BA], [QA] or [Dev], ending with "Answer with /devflow:answer #<n>, or reply on this issue with numbered answers." The issue is blocked once with all of them, not once per role.
   - **On blocked at any stage** (haiku, the blocked cleanup): commit nothing further; if the branch has commits, push it so work is not lost; comment on the issue with the stage, reason and question (the questions comment above when there are questions); exactly one comment per block carries the marker `<!-- devflow-blocked -->`: the questions comment as its second line (its first stays `<!-- devflow-questions -->`), otherwise the reason comment; delete the run's own `<!-- devflow-claim id=... -->` comment; label `labels.blocked`, remove `labels.inProgress`; remove the authenticated user from the assignees only when the claim returned `assignedByRun: true` (an assignee that was there before the run stays); `git switch <startBranch>`.
   - After blocked cleanup or a lost-claim release, a haiku agent checks whether this run’s claim comment remains. If present, the engine retries deletion of that claim once and checks again. The run records `claim not released` if the comment is still there.
   - **On a thrown error**: the stage work after a won claim is wrapped in try/catch. A stage agent that throws (in a parallel Implement both halves settle first) runs the same blocked cleanup once with stage `Error` and the first line of the message (`unknown` when empty), so the report entry is `blocked` with reason `Error: <message>` and the `assignedByRun` rule applies. A throw from the claim or release agent (claim not won) runs no cleanup: the entry is `blocked`, reason `Workflow error: <message>`, with the note `claim may be partial; run /devflow:doctor`. A throw from the cleanup itself is not retried: reason `Workflow error: <message>`, the notes so far plus `cleanup failed; run /devflow:doctor`, and the run continues with the next issue.
   - After each issue, a haiku agent runs the exact `devflow-run restore --to <startBranch>` command and returns its JSON. Ship and Blocked leave the checkout on the issue branch. A failed restore is noted and the remaining issues are skipped. Isolated worktrees stay on the issue branch.
   - **Chain** (`chain` true): each issue is stacked on the last issue of the lane that shipped (added to its parents unless already one), so the lane is a stack: each branch starts from that branch and each PR targets it. An issue that does not ship (blocked, or skipped, including claimed elsewhere) does not stop the lane: the next issue stacks on the last shipped one, or starts from the base when none shipped; only an issue with a real `Depends on` the failed one is skipped. Overlapping changes with the failed issue's branch, if it is finished later, are left to the gate and `/devflow:sync`.
3. **Report**: return `[{issue, status: pr|blocked|skipped, url?, prNumber?, risk?, stackedOn?, reason?, next}]`. `next` is one of `answer`, `merge`, `sync`, `nothing`, `check by hand`, computed in code by `nextStep` (exported for tests). A blocked entry with questions is `answer` (`/devflow:answer #<n>`); a blocked entry without questions, a skipped entry and any other non-PR entry is `check by hand`. For a shipped PR the precedence is: failing checks (`checksFailing`, read by the Ship agent; pending is not failing) give `check by hand`; then `mergeState` `conflict` or `behind` gives `sync` (`/devflow:sync #<pr>`, also for `risk:high`); then `risk:high`, or `decisions:review` unless `nextTask.trustDecisions` is true, gives `merge` (a human merges); else `nothing` (the merge gate merges it). `/devflow:next-task` prints `next` as the last column of its result table.

**Run limit.** `limit` counts issues worked on. An issue skipped at Claim (already taken, or the claim race lost) does not count toward the limit, so the next selected issue is worked on; a blocked issue, or a workflow error after Claim, counts. Issues past the limit are skipped with `over limit (N)`.

**Stacking.** The engine keeps a map of issues that shipped in this run (issue → PR number and branch) to resolve in-run parents. One parent: the branch starts from the parent's branch and the PR targets it. Several parents: Claim branches from the base, then **Integrate** (sonnet, schema `{ok, integrationSha, merged, problem}`) merges every parent branch with merge commits (no rebase), resolves conflicts between them, runs the checks and returns `integrationSha`; that SHA is the parentRef for Implement, Fix, Review and Blocked, and the PR targets the base with a "Stacked on #a and #b" line. The gate holds every PR whose linked issue still has an open `Depends on`.

**Parallel work.** One ticket per session, each session in its own worktree, started by hand (`/devflow:next-task #n --isolated`) or by `/devflow:dispatch`.

- *Changelog fragments* `bin/devflow-changelog` (node, no dependencies; `parseFragment` and `renderSection` exported for tests). One file `<fragmentsDir>/<issue number>.md` per issue, so parallel PRs never edit the same changelog lines. A fragment holds one or more `### <section>` headings (Added, Changed, Deprecated, Removed, Fixed, Security) each followed by at least one `- ` bullet; indented lines after a bullet (sub-bullets, continuation) belong to it; a repeated heading is merged; anything else, and any file in the directory not named `<number>.md`, is invalid. `has <n>` exits 0 for a valid `<n>.md`, 1 for a missing or invalid one, 2 for a usage error. `preview --version X.Y.Z --date YYYY-MM-DD` prints `## [X.Y.Z] - <date>` with sections in Keep a Changelog order, fragments by issue number ascending (numeric), each bullet ending ` (#<n>)` unless it already contains `(#<n>)`; it writes nothing. `assemble` (same arguments) writes that section below `## [Unreleased]` of `changelog.file`, puts the bullets that were under `[Unreleased]` first in their sections, then deletes the fragments; everything is validated before anything is written. Exit 1 (nothing written, nothing deleted): invalid fragment or file name, unknown heading or non-bullet line under `[Unreleased]`, version heading already present, changelog file or `## [Unreleased]` heading missing, nothing to release (no fragments and no bullets). Exit 2: `changelog.fragmentsDir` unset (every command), unknown command, missing or malformed `--version` (`X.Y.Z` or `X.Y.Z-pre.release`) or `--date`. Wiring: with `changelog.fragmentsDir` set, the implement and fix prompts tell the agent to add `<fragmentsDir>/<issue>.md` and never edit the changelog file, and the reviewer (prompt and `agents/reviewer.md`) checks that fragment, not the changelog, for the entry; without it the prompts are unchanged. `/devflow:release` shows `devflow-changelog preview` output in its notes and does not write it. `tests/docs.test.cjs` `changelogEntry(n)` finds an entry in `CHANGELOG.md` or in the fragment. This repository sets `changelog.fragmentsDir` to `changelog.d`.
- *Lane planner* `bin/devflow-lanes` (node, no dependencies; pure function `planLanes` exported for tests). Input `{maxLanes, ignoreHotspots:[], issues:[{number, hotspots:[], dependsOn:[]}]}` on stdin; output `{lanes:[{issues, sharedHotspots, ignoredTouched}], deferred:[{issues, reason}], stacked:[{issue, on}], ignoredHotspots, warnings}`. Hotspots matching `ignoreHotspots` (exact path, or glob with `*` and `**`; `[]` ignores none) are dropped before grouping and echoed in `ignoredHotspots`: docs files like the README and CHANGELOG are touched by most tasks and their conflicts are small (the gate's branch update or `/devflow:sync` resolves them), so they would otherwise merge every task into one lane. Per lane, `ignoredTouched` is the sorted list of ignored hotspots (exact path, so `docs/a.md` and `docs/b.md` differ) named by the lane's issues that an earlier lane's issues also name; `[]` when none and for the first lane. Union-find: two issues join when they share a hotspot (exact, case-sensitive, trimmed path; transitive) or form a linear dependency link with one in-set child per parent and one in-set parent per child. Fan-out and multi-parent children go to `stacked` unless a shared hotspot joins them to a lane. Dependencies outside the set are ignored. Inside a lane: topological order, parents first, ties by smallest number; a cycle falls back to number order with a warning. Lanes sorted by their smallest issue number; lanes beyond `maxLanes` (default 3) go to `deferred` with reason `over maxLanes (N)`. Invalid input: message on stderr, exit 1. Why this shape: tasks that touch the same files share a lane and stack on each other, so parallel lanes never touch the same files and never conflict; stacking inside a lane replaces rebasing and merge conflicts.
- *`/devflow:dispatch [max lanes]`* (`disable-model-invocation: true`, no commits, never merges). Preflight: config, GitHub MCP, `claude --version`, clean tree. Sweep approved epics before collecting work. With `--plan`, preview ready labels without writing them. Collect open ready issues using the Select rules, including the exception for a resumable devflow PR. Apply the eligibility sweep’s dependency rule. Open parents without PRs can be planned in the same batch if schedulable. Report blocked or unavailable dependencies as waiting with the reason. Report each `stacked` child as waiting for its parents to open PRs, with no session. Once the parents have qualifying PRs, the engine stacks the child on the parent branch or the Integrate commit for several parents. Build `{number, hotspots, dependsOn}` per issue (hotspots from the body's `## Hotspots` bullets, backticks stripped, bare "None" skipped). `maxLanes` = argument, else `dispatch.maxLanes`, else 3; `ignoreHotspots` = `dispatch.ignoreHotspots`, default `["README.md", "CHANGELOG.md"]`. Print the plan (lanes, order, shared hotspots, ignored hotspots, deferred, waiting) and each lane's `ignoredTouched` as the files where `/devflow:sync` may work; with `--plan` stop there (no session, "nothing to run" when no lane), otherwise continue without asking again, and start lane n with `claude --bg "/devflow:next-task #a #b --chain --isolated"` (plus `--plugin-dir <dispatch.pluginDir>` when set; `--chain --isolated` even for a one-issue lane). If `claude --bg` fails, stop starting lanes and print the `claude -w lane-<n> "..."` command for the failed and remaining lanes. Report: lane → session id → issues, plus each lane's `ignoredTouched`; follow with `claude agents`, `claude logs <id>`, `claude attach <id>`.
- *Safety nets.* The claim (above) is what makes a double start harmless: a second session on the same issue skips it. A broken lane stops at the first issue that does not ship. Worktrees are created under `worktree.dir`, ignored by git, and removed only when clean and fully pushed.

**Verified behaviour** (spike on the real machine, not assumed):

- `claude --bg --plugin-dir <dir> "/plugin:skill"` expands the plugin skill in the background session.
- A `claude --bg` session did **not** move into a worktree by itself (its Bash ran in the main checkout). So devflow creates the worktree itself (`--isolated`) and does not rely on background auto-isolation.
- After EnterWorktree, Workflow agents run in the session's worktree directory.
- `claude --bg` needs a trusted workspace ("Workspace not trusted" otherwise), and the background session cannot answer permission prompts, so the project needs allow rules (or an auto permission mode); `/devflow:init` offers them.
- A fresh worktree needs its own setup (`worktree.setup`, e.g. `make setup`, took ~3 s on TaskBoard).

**Test hook.** `args.exports === true` returns the pure helpers (`parseDiff`, `scanWeakenedChecks`, `checkConfigGlobs`, `globToRegExp`) before anything else runs. They are function declarations, so they are hoisted, and they take every input as a parameter.

**Spec read.** `specPathFor(issue)` takes the first `<specDir>/…md` path from the issue body. Implement starts with `git show <baseRef>:<path>` and must return `specRead` containing the path; otherwise one Fix round re-checks the change against the spec, and a second miss blocks the issue. Review is pointed at the same path.

**Epic as the spec source.** `epicFor(issue)` takes the number from the first line of the body matching `^Epic: #(\d+)` (0 when there is none). Source rule: a spec path in the body (or from Claim) wins, also when the body has an `Epic:` line; else the epic; else the issue alone. For an epic the Plan, Implement (single and dev half), QA, Fix and Review prompts tell the agent to read epic `#<n>` (MCP `issue_read`, method `get`; the `devflow:reviewer` agent with `gh issue view <n> --repo <owner>/<repo> --json title,body`) for shared design and decisions, take criteria and Test cases from the issue, and let the issue's `## Decisions` win. `specRead` must contain `#<n>` as a whole token (`#420` is a miss for epic 42). The Plan, Implement (also used by Fix), QA and Review schemas have an optional `epicRead`. An explicit `epicRead: false` means the epic is missing, closed, a pull request or unreadable. A missing epic token in Implement gets one corrective Fix when Implement did not explicitly report the epic unreadable. With `nextTask.onQuestion: "decide"` (the default), an unreadable epic or a missing epic token at Plan, QA or after the corrective Fix lets the stage continue using the issue's criteria and Test cases. The engine adds `epic #<n> could not be read at <stage>; continued on the issue's criteria and Test cases` once per stage to the run notes and the PR's Decisions taken, and labels the PR `decisions:review`. With `onQuestion: "block"` these failures block at the reporting stage. A missing spec file read still follows the spec read rules above. An issue with neither a spec path nor an `Epic:` line asks for no read and never blocks on `specRead`.

## `/devflow:sync [#pr ...] [--unattended]`

Not `disable-model-invocation`: a scheduled `/loop` prompt arrives as plain text and Claude can only run a skill through the Skill tool, which that flag blocks, so `/loop 15m /devflow:sync` could never run. Sync is the one skill meant to run unattended; its description limits model invocation to a user request or a `/loop` prompt naming it. An unattended run (`--unattended`, the form to use in a loop, or a run evidently started by `/loop`) asks nothing: a thread needing a product decision stays unresolved and is listed as "needs a human". It works in a temporary worktree of `<remote>/<baseBranch>` (removed in every case, never touching the user's checkout), stops at once with "nothing to sync" when there are no targets, and keeps the round limit as its safety stop. Interactive runs are unchanged. Replaces `/devflow:address-reviews`. Default targets: open PRs labelled `labels.devflow` and authored by the current user; explicit `#pr` numbers override. Needs a clean working tree; the starting branch is restored at the end. Fork PRs are skipped. PRs are processed parents before children. Only new commits and normal pushes: no rebase, no force push, no merge.

Per PR:
1. **Retarget.** If the PR is stacked and its parent PR is merged (or the base branch is gone), change its base to `baseBranch` (`update_pull_request`) and remove `labels.stacked`.
2. **Update when behind.** If behind and it merges cleanly, `update_pull_request_branch`, except that a PR the merge gate updates is skipped: `mergeGate.enabled` true, `mergeGate.dryRun` false, labelled devflow and `risk:low`, targeting `baseBranch`, not blocked. Every other behind PR (gate off, dry run, `risk:high`, stacked, blocked) is updated; retargets and conflict resolution still run.
3. **Conflicts.** Merge `<remote>/<base>` into the branch (a merge commit, never a rebase). Resolve each conflict from the linked issue and spec, keeping both behaviours when compatible; run `checks`; commit `merge(<scope>): sync with <base>`; push. Then remove `labels.blocked` from the PR and its issue (the gate adds it on conflict), unless something else blocks the issue. If a conflict cannot be resolved with confidence or checks fail: `git merge --abort`, label the issue blocked, comment with the files and the one question for a human.
4. **Review.** Only trusted authors are acted on: a thread's first-comment author must be the authenticated user, the review bot (login `claude`, counted as the bot only when `get_reviews` shows a review by `claude[bot]`) or a login from `list_repository_collaborators`; no other bot is trusted. The review summary comment counts only from `claude[bot]` or the authenticated user, even with a `<!-- devflow-verdict` marker. Other threads and summaries are listed as `ignored: not a collaborator` and get no reply and no commit; untrusted replies inside a trusted thread are ignored; sync never resolves a thread it did not start. Unresolved, actionable threads are classified fix / answer / won't fix (reason, citing CLAUDE.md or the spec); a thread needing a product decision goes to the user. Fixes are new commits (`fix(<scope>): address review - <what>`), `checks` must pass, push, then reply on every thread. A reply lets the merge gate treat a thread started by the PR author or the review bot as answered; a thread started by another trusted human (OWNER, MEMBER, COLLABORATOR) blocks the gate until that human resolves it. No re-review comment is posted: the push re-runs the review.
5. **Round limit.** A round is a run of step 3 or 4 that changed or answered something. Rounds are counted by the hidden marker `<!-- devflow-sync -->` in earlier comments; at `nextTask.maxReviewRounds` the PR is left for the user. After a round, one marker comment with a one-line summary is posted. Steps 1 and 2 are not rounds.
6. Switch back; summary table PR → retargeted / updated / conflicts / threads fixed, answered, won't fix, `ignored: not a collaborator` / rounds left.


## `/devflow:approve #<epic>`

An explicit human command. It uses GitHub MCP to add `labels.epicApproved` (default `epic:approved`) and applies the eligibility sweep once. The owner can also add this label directly. The optional `spec.autoReady` setting defaults to `off`. With `low`, the sweep requires `labels.riskLow`. With `all`, it accepts any risk. The risk labels and rules for merging PRs still apply.

The sweep considers open native sub-issues and issues with an exact `Epic: #<epic>` body line in the configured repository. It skips issues already ready, in progress, in review, blocked or in triage. Every `Depends on #n` issue must be closed or have an open PR at least one commit ahead of its base and carry no blocked label. Parent risk does not affect eligibility. The child must have no `Ready: manual` line, and its `## Open questions` section must be absent, empty or `None`. Approval is checked before writes. Removing it stops future sweeps and leaves existing ready labels in place.

The command reports each sub-issue and its action (`ready`, `waits for #n`, `manual`, `high risk` or `open questions`). Dispatch applies the same sweep before collecting ready issues. `--plan` previews eligibility and lanes without posting a label or comment.

## `/devflow:autopilot #<epic>`

Each tick verifies epic approval, syncs the epic's devflow PRs, processes trusted comments, applies the ready sweep and starts background lanes. The pure `bin/devflow-autopilot` helper uses the supplied activity timestamps to detect stalls and calls `planLanes` with the remaining slots. `autopilot.maxLanes` inherits `dispatch.maxLanes` (default 3). Each lane start costs one of `autopilot.maxAgentCallsPerTick` (default 20). Running issues idle longer than `autopilot.stallHours` (default 12) keep their slots and are reported for human attention.

The marked epic comment stores the plan, session IDs and comment cursor alongside a progress table. A restarted loop resumes there. Once every sub-issue is closed, autopilot posts the final report and ends the loop.

## `/devflow:answer #issue [1: answer; 2: answer ...]`

`disable-model-invocation: true`. Unblocks an issue that the engine blocked with questions. Needs a clean working tree. GitHub via the MCP server. Never merges, never pushes to `baseBranch`.

1. **Questions.** Find the latest issue comment starting with `<!-- devflow-questions -->` whose author is the authenticated user or has `author_association` OWNER, MEMBER or COLLABORATOR (forged questions comments are not used); none → nothing to answer, stop.
2. **Answers.** From the arguments (`1: ...; 2: ...`), else from comments posted after the questions comment by the authenticated user or authors with `author_association` OWNER, MEMBER or COLLABORATOR, never bots; the latest trusted answer per question wins and other comments are reported as `ignored: not a collaborator`. Every question needs an answer; otherwise list the unanswered ones and change nothing.
   **accept.** `/devflow:answer #n accept` answers every open question with its `Recommended:` option; `accept; 2: <answer>` takes the recommended options for all questions except question 2, which takes the typed answer. `accept` refuses a question whose recommended option changes an acceptance criterion (the questions comment marks it `[changes a criterion: typed answer needed]`) and asks for a typed answer for it; no answer is recorded until all are answered. `accept` with no open questions says so and changes nothing; an override number out of range or repeated refuses the whole answer.
3. **Spec (BA role).** Only when the issue has a spec path; with none, no branch and no PR. Branch `docs/<issue>-answers` from `<remote>/<baseBranch>`; the only change is appending `- <date> (Q<k>): <question> → <answer>` to the spec's `## Decisions` section (created at the end if missing); no other spec line changes. Commit `docs(#<n>): record answers to open questions`, push, open a PR to `baseBranch` labelled `devflow` + `risk:low` (`risk:high` if the spec path matches `risk.highPaths`), `Refs #<n>` (not Closes). If PR creation fails, the user gets a pre-filled compare link.
4. **Issue body and epic (BA role).** Append the same entries to the issue's `## Decisions` section (created at the end of the body if missing; Plan and Implement treat it as overriding the spec). No acceptance criterion or Test cases row is edited. When the body has `Epic: #<n>`, also append `- <date> (#<issue>, Q<k>): <question> → <answer>` to the epic's `## Decisions` (read the body, write it back whole), with or without a spec path. A failed epic append is reported in the final table and the unblock comment; the issue's entries stay.
5. **Unblock.** Delete every `<!-- devflow-claim id=` comment, remove the assignee devflow set, remove `labels.blocked` and `labels.inProgress`, add `labels.ready`, post one comment (answers, where the decisions were recorded: issue, epic, spec PR link, "Ready again: run /devflow:next-task #<n>").
6. **Report.** Table question → answer, the spec PR, the epic append result, the issue's labels. A branch left over from a run blocked at Plan is reused or recreated by Branch; a branch with commits from an earlier blocked run is resumed by the engine.

## `/devflow:accept <epic #n | spec path or slug>`

`disable-model-invocation: true`. The BA step after merge: does what shipped match what the spec promised? Changes no tracked file, makes no commit, never merges. Preflight: config, GitHub MCP, clean tree, fetch. Without `verify.devServer`, or with empty `verify.modes`, it does not stop: it runs in evidence-only mode (no worktree, no lock, no server). Criteria that need a running app are `not checkable`; the others take their result from the merged PRs' checks, test-matrix rows and manual rows recorded as pass in the PR body, and a criterion with no such evidence is `not checkable`. It still posts the `<!-- devflow-accept -->` result on the epic or spec PR.

1. **Resolve.** `/devflow:accept #<n>` (or `<n>`; a number is always an issue number, never a slug) takes an epic: the issue set is the union of the epic's native sub-issues (`issue_read get_sub_issues`) and the issues whose body has `Epic: #<n>`; criteria and `http` / `e2e` Test cases rows come from each sub-issue; with neither source the run stops with `#<n> is not an epic` and posts nothing. Gap titles use the slug from `[<slug>]` in the epic title, else `[epic #<n>]`. For a spec path or slug: the spec is read from `<remote>/<baseBranch>` only (not there → its PR is not merged, stop). List tasks, criteria and the Test matrix rows with level `http` or `e2e`; find the issues whose body links the spec (matched to tasks by `T<n>` in the title) and their closing PRs. Only merged issues are accepted; none merged → nothing to accept.
2. **Fresh worktree** of `<remote>/<baseBranch>` under `worktree.dir` (`accept-<slug>`), `worktree.setup` run in it: what shipped, not the user's checkout.
3. **Verify lock** (`verify.lock`), same lock as Verify.
4. **Walk** every criterion of every merged task plus those matrix rows with the allowed `verify.modes` (curl, or the configured browser tool), run with `accept.model` (`sonnet` default, an Agent of that model when the session differs). Result per criterion: `pass`, `fail` or `not checkable`, with expected versus actual evidence. The dev server, lock and worktree are always cleaned up.
5. **Gaps.** Each `fail` without an open duplicate is drafted from the bug template `skills/spec/templates/bug.md` as an issue `[slug] Gap: ...` (Context, Expected, Actual, Repro, Introduced by, a suggested Risk, Acceptance criteria, Scope, Test cases, Dependencies; labels `labels.triage` and `accept.labels`, no ready, risk or priority label), followed by a comment suggesting a priority and a risk with reasons. A human sets those labels and ready. One yes for the whole batch; declined → none created. `not checkable` items are listed for a human and get no issue.
6. **Report.** One comment starting `<!-- devflow-accept -->` on the spec PR (on the epic for an epic argument, which no skill closes) (table, counts, issues left out, gap links), edited in place on a re-run. Gap issues are picked up by `/devflow:next-task` once a human sets them ready; `/devflow:release` includes the result. The result also lists the open follow-ups filed from the epic's PRs (open `labels.triage` issues whose `Found in: #<pr>` names one of them): a list for a human, no issue is created, changed or closed for it.

## `/devflow:release <spec | since <tag> | all> [--version X.Y.Z]`

`disable-model-invocation: true`. Config `release`: `tagPrefix` (`v`), `draft` (true), `deploy` (empty), `notesFrom` (`prs`). Never merges, never pushes tags from the shell; the GitHub release creates the tag.

1. **Collect** the merged PRs labelled `labels.devflow` with base `baseBranch`: for a spec, the PRs closing its issues plus the spec PR; for `since`, those merged after the tag (latest tag with the prefix when none is named); for `all`, every one (the proposed default when no tag exists). `spec:` PRs are included. Refuse while one of the spec's issues has an open PR (unless the user says release anyway); an issue with no PR is listed as not shipped.
2. **Version.** `--version` wins (stop if the tag exists); otherwise propose the next semver from the Conventional Commit types: a breaking change (`!` or a `BREAKING CHANGE` footer) major, any `feat` minor, otherwise patch; `0.1.0` with no earlier tag. The user confirms. **Predecessor check** first: when the previous released version (the newest semver heading of the changelog) has no tag `<tagPrefix><version>`, the skill refuses to propose a version, names it, and continues only after the user says so; skipped when there is no earlier version heading, non-semver headings are ignored.
3. **Notes** in English: **What's new** first (client-facing, grouped by spec, no numbers or internal names), then a **Changelog** with Features, Fixes (those whose linked issue has the first `labels.priority` label first, marked critical), Docs (including `spec:` PRs), Chores (empty ones omitted, one line per PR); **Risk** (each `risk:high` PR and who merged it, or "No high-risk changes.", plus gate versus human: the gate marks its merges with a `<!-- devflow-gate-merged -->` comment and a `Merged-by: devflow merge gate` trailer; older PRs show "merger unknown (gate or owner)" when the gate token owner merged); **Acceptance** (counts and gap links from the `<!-- devflow-accept -->` comment, or "not run"). Shown for a yes.
4. **Create the release** with the MCP server (title = tag, target = the base head commit, `draft` per config). Without a release tool: a pre-filled `releases/new` link and the notes.
5. **Deploy** only when `release.deploy` is set, and only after a separate explicit yes (a yes for the release is not one for the deploy; a draft has no tag yet, which is said). Exit code and the last 20 lines are reported; no retry.

## `/devflow:report <spec path, slug or #epic>`

`/devflow:report --daily [#epic]` prints a Markdown digest for the named epic or each open approved epic. It lists PRs awaiting review, flagged decisions, run-error bugs, waiting reasons, and PRs merged and issues closed since local midnight. Cost sums the per-issue `agentCalls` recorded when Ship builds each reported PR's `devflow-run` marker and counts PRs with missing data as unknown. Autopilot uses the same `bin/devflow-digest` renderer to post one dated comment per epic per local day, saves `lastDigestDate` in the plan and refreshes the completion day's comment at the end.

`/devflow:report #<n>` takes an epic: the issues are the union of its native sub-issues and the issues whose body has `Epic: #<n>`; `spec.epic` is `{ number, url }` (`null` for a spec file) and `spec.pr` is `null`. Each issue gets `metrics`: `{ path, reviewRounds, blocked, claimedAt, mergedAt, durationHours, mergedBy }`, taken from the PR used (the merged PR that closes the issue, else the latest), its `devflow-run` marker (review rounds fall back to the verdict-marker count, else `null`), the count of `<!-- devflow-blocked -->` comments, and the who-merged rule; `durationHours` is claim to merge in hours with one decimal. The trace shows five metrics (path, review rounds, times blocked, duration, merged by); `claimedAt` and `mergedAt` stay in the data; `null` renders as "unknown"; 2.9.0 data without `metrics` still renders.

`disable-model-invocation: true`. Read-only on GitHub and the repository; posts nothing and commits nothing. For each issue of a merged spec it collects, with `null` for what does not exist (never invented): the spec PR and who merged it (gate or human by the gate's merge marker, or unknown; i.e. Gate 1), the plan comment, the questions comment and whether answers followed, the closing PR (stacked or not, merged by), the `devflow/review` status and the number of review rounds (distinct head SHAs with a verdict marker), the tests in the diff (files, count, matrix rows covered, whether the first commit is a `test(...)` commit), the acceptance comment and the release. It builds one JSON object with a fixed shape, injects it into `skills/report/templates/trace.html` (the `{{TRACE_JSON}}` placeholder in `<script type="application/json" id="data">`, with `</` and `<!--` escaped; nothing else in the template changes) and publishes the page as an artifact (an existing artifact URL is updated in place). Steps without data show grey. It exists for demos: the flow ticket → plan → PR → review → tests → merge → acceptance → release with who acted at each step and a link to the evidence, not slides.

## `/devflow:doctor [--fix]`

`disable-model-invocation: true`. Read-only by default; with `--fix` it changes only what the user confirms (item by item, except the one confirmation for the merged-branch list in check 5). Never merges, force pushes, pushes to or deletes the base or a protected branch. Runs every check even when one fails; without a config, check 1 fails and only checks 3, 8, 9 and 10 run.

1. **Config**: parses and validates against the schema; `devflowVersion` with a lower major or minor version, or missing → warn (a lower patch version only is ok), suggest `/devflow:init --upgrade`.
2. **Templates**: drifted installed templates (same comparison as `--upgrade`); report only.
3. **GitHub access**: probes each connected GitHub MCP server for the authenticated user (fail when none answers); reports the tool prefix of the server it used (the allowed one that answered, if any), and warns only when `.claude/settings.json` allows another GitHub MCP prefix and no allowed prefix belongs to a server that answers (ok when an allowed prefix answers, so several authenticated servers give no false warn; no allowed prefix is left to check 8); `gh` missing is a warn (runs stop when the MCP connection drops).
4. **Worktrees** under `worktree.dir`: clean or dirty, branch pushed or not. `--fix` removes clean ones whose branch is pushed (no `--force`) after a yes per item, never a dirty one; worktrees of merged devflow PRs are left to check 5.
5. **Branches**: for every PR labelled `devflow` with a non-null `merged_at`, doctor lists the leftover remote head branch, local branch and worktree; without `--fix` it only lists. `--fix` asks ONE confirmation for the whole merged list, then re-checks each item before deleting it (`merged_at` still set; no open PR has the branch as base or head; not `baseBranch`, not in `protectedBranches`, not the current branch; a worktree is not the directory doctor runs in) and skips it with the reason when a re-check fails. Deletion uses only guard-compatible commands: `git worktree remove` without `--force` (a dirty worktree is kept and reported), `git branch -d` (on refusal it prints `git branch -D <branch>` for the user; the guard blocks `-D` for Claude), `git push <remote> --delete <branch>` with `<remote>` = `github.remote` (default `origin`). Branches of PRs closed without merging keep a separate yes per branch, re-checked the same way except that the PR must still be closed with `merged_at` still null (not reopened or merged) instead of `merged_at` still set. The check also reads the repository setting "Automatically delete head branches" (`gh api repos/<owner>/<repo> --jq .delete_branch_on_merge`): `warn` when off, `unknown` when unreadable, `ok` when on. The guard hook is unchanged.
6. **Idle in-progress issues**: report open in-progress issues with no running session, no open PR and a claim older than 2 hours. After confirmation, doctor `--fix` re-checks those conditions, deletes the idle run’s claim comment, swaps in-progress for ready and removes only the authenticated user as assignee, if assigned.
7. **Open PRs** labelled `devflow` that are behind, conflicting or red: reported with `/devflow:sync #<pr>`, never fixed here.
8. **Allow-list** in `.claude/settings.json` for background sessions (`bin/devflow-setup allow`): missing rules listed; `--fix` merges them in, never a deny rule or a rule that allows merging or pushing to a protected branch.
9. **Owned by the plugin now** (`bin/devflow-setup leftovers`): `.claude/hooks/block_git_add_all.py` and its test, the settings hook that runs it, a `hook-test` style `checks` entry, deny rules the guard enforces, a maintenance `.claude/loop.md`, a project `.claude/agents/code-reviewer.md`. Each is a `warn` with what replaces it; doctor never deletes them, also not with `--fix`.
10. **Guard**: run the guard against a merge tool call and expect exit 2. Report a failure if it does not block the call. Read-only.
11. **Release tag**: the declared version (`version` in `.claude-plugin/plugin.json`, else the newest changelog version heading) must have the tag `<release.tagPrefix><version>`; missing tag → warn naming it, and plugin.json and changelog disagreeing → warn. Skipped when the project has neither. Read-only.
12. **Stale follow-ups**: open `labels.triage` issues titled `[follow-up #...]` are checked against the base. With a recorded `file:line` (the `Found in:` follow-up format), `git log -L` on `<remote>/<baseBranch>` for those lines showing a commit after the issue was created makes it stale; a deleted file counts as changed. Without a `file:line` record, a merged PR that mentions `#<n>` makes it stale. A hit is a `warn` "may be fixed, check and close". Doctor never closes, edits or comments on the issue, also with `--fix`. Read-only.
13. **Closed issues with state labels**: list closed issues carrying `labels.inProgress`, `labels.review` or `labels.blocked`. With `--fix` and confirmation, remove those labels after checking that the issue is still closed.
14. **Stale claims**: list `devflow-claim` comments on open issues with no `labels.inProgress` and no open PR. With `--fix` and confirmation, re-check those conditions and delete the listed claim comments.

Output: a table check → `ok` / `warn` / `fail` → what to do, a line per fix applied or declined, and the one command to run next.

**Waiting on you** (last section of the output, read-only, never changes anything, also with `--fix`): one line per item with one command. Categories in order, each issue or PR once in the first matching one: blocked issues with open questions (`/devflow:answer #n`), PRs waiting for a human merge, PRs in conflict or behind (`/devflow:sync #pr`), ready issues (`/devflow:next-task` or `/devflow:dispatch`), sub-issues of an open epic without `labels.ready`, epics whose sub-issues are all merged and have no accept result (`/devflow:accept #n`). An item it cannot classify is listed as "check by hand"; with nothing to do it says so; no cap on lines.

## Release process

The steps live at the bottom of `CHANGELOG.md`, which is the release task template; this is the design behind them.

- Bump the version everywhere `tests/version.test.cjs` checks. With `changelog.fragmentsDir` set, the release PR runs `node bin/devflow-changelog assemble --version X.Y.Z --date YYYY-MM-DD` and commits the result; otherwise the items under `[Unreleased]` move to the new heading by hand.
- The upgrade note of a release that changes a reusable workflow tells callers of the reusable workflow to move their pin to the new tag.
- **Smoke run before the merge.** In the sandbox repository `nhanle-agilityio/devflow-sandbox` (fixtures only, never reset): load the plugin from the release branch with `--plugin-dir`, create two fresh issues from the fixtures `docs/smoke/low.md` (`risk:low`) and `docs/smoke/high.md` (`risk:high`), start them with `/devflow:dispatch` as two lanes (each runs `/devflow:next-task`), then run `bin/devflow-smoke --expect low` and `bin/devflow-smoke --expect high` on them. The release PR records the number of conflicts, "behind" updates and `/devflow:sync` calls the lanes needed. A human merges the release PR only when both checks pass; a docs or UI change also needs its manual rows checked by a human before the merge.
- A human tags `vX.Y.Z` on `main` right after the release PR merges, so pinned callers and the doctor's tag check never see a declared version without its tag. Claude never merges or tags.
- *Smoke checker* `bin/devflow-smoke --repo owner/name --issue <n> --expect low|high` (node, no dependencies; `run`, `check`, `ghArgs` and `makeGhReader` exported for tests). Every GitHub read goes through one reader function (API path → parsed JSON, `null` for a 404); the default runs `gh api -X GET <path>` and never passes a field or input flag, after `gh auth status` succeeds (`gh` missing or unauthenticated: message on stderr, exit 2). Closing PRs are the pull requests of the same repository in the issue's timeline (`cross-referenced`) whose body has a closing keyword for `#<n>` and that are open or merged. One line per check, `ok <check>: <detail>` or `fail <check>: <detail>`: `issue` (exists and is not a PR; `low` also needs it closed, `high` accepts open), `closing PR` (exactly one, labelled `devflow`), `run marker` (`<!-- devflow-run {...} -->` with `path` and `reviewRounds`), `review` (a `## Review` section), `risk line` (`Risk:` matches `--expect`), `merge` (`low`: merged with the gate's `<!-- devflow-gate-merged -->` comment or the `Merged-by: devflow merge gate` trailer on the merge commit, either counts; `high`: open, or merged with neither), and for `high` `risk label` (`risk:high`). A missing issue fails every check. Exit 0 only when all pass, 1 when one fails, 2 for a usage error, `gh` missing or unauthenticated, or a read error. The labels are the defaults (`devflow`, `risk:high`), as in the sandbox.

## Risk and the merge gate

Risk flows: spec task (`risk` + reason, approved by the ready label on the sub-issue, or at Gate 1 with `--file`) → issue label and `Risk:` line → engine (escalate to high on `risk.highPaths`; unlabelled = high) → PR label and body line → gate (acts only on `risk:low`).

**Merge gate** = `.github/workflows/devflow-merge-gate.yml` + `.github/scripts/devflow-merge-gate.cjs`, installed by `/devflow:init`. It exists because target repos may be private on GitHub Free. Runs on `workflow_run` completion (CI workflows and "Claude Code Review"), `status`, and manual `workflow_dispatch` (optional PR number). The workflow lives on the default branch (those triggers only run from there) and uses `DEVFLOW_GATE_TOKEN`, a fine-grained PAT scoped to this repository with Contents and Pull requests read/write, plus Issues read/write for auto-readying, because pushes and merges made with `GITHUB_TOKEN` do not trigger CI. Config is read from `.claude/devflow.json` at `baseBranch`. It does nothing unless `mergeGate.enabled`; with `dryRun` (default) it only reports. A PR labelled `labels.decisionsReview` (default `decisions:review`: the run took decisions) is skipped with `decisions:review: waits for a human`, checked right after the `risk:high`, no-risk-label and blocked checks and before any API call, unless `nextTask.trustDecisions` is `true` (default `false`); with trust on the PR is evaluated like any `risk:low` PR, so a high-path file, a conflict, a behind branch, a failing check or a blocking thread still hold it. The workflow's inputs and secrets are unchanged.

Every enabled run sweeps one page of up to 100 recently updated closed issues in its repository, even when no PR is eligible or there are no effective required checks. The gate also cleans linked issues after merging a PR. Cleanup removes the configured `labels.inProgress`, `labels.review` and `labels.blocked` labels that are present. Dry runs log sweep removals, and removal failures warn without stopping cleanup.


After its own merge, the gate reads the epic body reference on each issue the PR closes. It sweeps each affected approved epic once, using fresh dependency states. It adds the ready label to each eligible child and posts `Ready: epic #<epic> approved, all dependencies merged` with the `<!-- devflow-auto-ready -->` marker once per issue. Failures warn and the gate continues. In dry-run mode it projects the PR's issue closures and logs the ready actions without making changes.

Per run it walks open PRs labelled `labels.devflow` in priority order (`priorityRank` of the linked issues' labels, the best one when several; the PR's own labels when it links none; then PR number) and **merges at most one**. Priority changes only the order: every rule below still applies. Rules in order; the first failure decides:

1. not a draft; not `risk:high`; has `risk:low`; not `labels.blocked`;
2. base is `baseBranch` (a stacked PR waits for its parent);
3. none of the PR's files (new or, for a rename, previous name) matches `risk.highPaths` or the built-in `.github/**` and `.claude/**`: the label is a claim set by an agent, the file list is re-read on every run. A match skips the PR and relabels it `risk:high` (dry run: `would skip`, nothing changed). This runs before any update-branch, so a high-path PR is never touched;
4. mergeable (not yet computed → skip; conflicts → label the PR and its linked issues blocked, comment once pointing at `/devflow:sync`);
5. not behind its base; if behind, `update-branch` (CI re-runs), but only for the first such PR of a run (see the update slot below);
6. every effective required check is green on the head SHA (check run or commit status; the effective list is `mergeGate.requiredChecks` without `devflow/review` while `review.github` is off, the list as is when it is on; a `devflow/review` commit status counts only when `github-actions[bot]` created it). Whenever the effective list is empty (flag off with only `devflow/review`, or `[]`) the gate runs no candidate rule: no update, relabel, conflict block or merge, also in a dry run, and every candidate is `skipped` with `no required checks (devflow/review is ignored while review.github is off); refusing to merge`. This closes the old gap where `[]` merged with no check. The callers' triggers do not change;
7. no blocking review thread. Only unresolved, not outdated threads count, judged by the thread's first comment: a thread started by a human (`__typename` `User`, whatever the login) with association OWNER, MEMBER or COLLABORATOR blocks until it is resolved or outdated, even when the PR author replied last (a reply is not a resolution); a human with any other association (CONTRIBUTOR, NONE, ...), a deleted user (no author) or a missing association does not block. A thread started by the PR author, or by the review bot (`__typename` `Bot`, login `claude`), blocks only when its last comment is not by the PR author. A thread started by any other bot (`coderabbitai`, `copilot-pull-request-reviewer`, ...) never blocks. Logins are compared without the `[bot]` suffix, so a bot PR author's own replies count as the author's. Caveat: a private organisation membership shows as `CONTRIBUTOR`, so such a reviewer's thread does not block; make the membership public or resolve through the review.

**Update slot.** One run updates at most one branch, so several behind PRs do not each trigger CI and then fall behind again as the first one merges. The first eligible behind PR in priority order takes the slot and is `updated` (dry run: `would update`); every later behind PR is `deferred` with reason `deferred: waits for its turn`. A PR skipped by an earlier rule (draft, risk, blocked, stacked, open dependency, high-risk file, conflict, mergeability not computed) never takes the slot, and neither does a PR whose `updateBranch` call throws (action `error`). An up-to-date PR also holds the slot while it is *in flight*: at least one required check is running (run `queued` or `in_progress`, or commit status `pending`) and none is failed (a completed run without `success`, or status `failure` or `error`). It is then `skipped` with its check reason and later behind PRs are `deferred`. A failed check (also next to a running one), only missing checks, or a run in `waiting` or `requested` do not hold the slot. An update does not stop an up-to-date, green PR later in the order from merging in the same run; after a merge, behind PRs are `deferred: one merge per run` and nothing is updated. The gate uses no clock. Two windows are accepted: a `pending` commit status that never resolves holds the slot and blocks updates until it is re-run or replaced (re-run the check, or post a new status for that context); and an in-flight check can still fail after it held the slot for a run, which frees the slot at the next run.

Then: merge with `mergeGate.method` (merge commit) pinned to the head SHA, retarget open PRs based on the merged branch to `baseBranch`, delete the head branch (same-repo, not a protected name). The run summary lists every PR with action and reason. `tests/merge-gate.test.cjs` covers each rule against a fake Octokit.

Post-merge mode runs on `pull_request: closed` for merged same-repository PRs. It applies the existing auto-ready rules to the merged PR’s linked issues and moves open devflow-labelled PRs stacked on a devflow-labelled, unprotected head to the merged PR’s base. Dry runs report the projected actions in the job summary. A repository gets this mode only after upgrading its caller with `/devflow:init --upgrade` to a release that includes it.

**Review check** = `claude-code-review.yml`, optional via `review.github` (default false): its first step `flag` reads `.claude/devflow.json` through the API with the gate's lookup (default-branch copy only to learn `baseBranch`, then the copy at `baseBranch`, which wins; a failed read of it falls back to the default-branch copy; never the PR head, so a PR cannot switch its own review). `enabled` is `'true'` only when `review.github === true`; otherwise every later step is skipped (no status, not even pending, no Claude call), the job succeeds and the step summary says `devflow review is off (review.github is not true)`; when no copy can be read it is off with a warning. Accepted trade-off: with the flag off no independent party confirms the review, and a PR opened by hand (no `devflow` label) gets no review; the owner runs a local review (`devflow:reviewer`). When on, it sets `devflow/review` pending, reviews with Opus (correctness, tests incl. Test cases rows, scope, CLAUDE.md, and as critical: weakened checks and out-of-scope items that contradict the acceptance criteria), ends its summary comment with a hidden marker `<!-- devflow-verdict {sha, verdict, critical, warning} -->` and publishes `devflow/review` from the bot's latest marker: success only for `pass` on the current head SHA, failure for changes, a missing marker or another SHA. (A verdict file was dropped: Claude Code read the absolute-path Write rule as project-relative and the write was denied.) It runs on open, ready, reopen and every push. If the only commits since the last bot-published result are clean base merges (two parents, made by GitHub's web-flow), it copies that result to the new head instead of re-reviewing, but only when it is a real verdict (success, or a failure described as "N critical, M warning") and the commits since do not change `.github/workflows/claude-code-review.yml`; anything else (e.g. "No verdict ...") is reviewed again. Concurrent runs for one PR are cancelled. The `devflow/review` status is created with `GITHUB_TOKEN` and does not fire `status` events, which is why the gate also listens for the review workflow's `workflow_run`.

## Run helpers

`bin/devflow-gh` checks PATH for an executable `gh` file and returns a JSON boolean field named `gh`. Next-task preflight uses it to set `ghCli`.

### `bin/devflow-run`

`check [--config .claude/devflow.json]` runs configured checks sequentially through `/bin/sh -c` in the current directory, continuing after failures and timeouts. Each check defaults to 600 seconds and can set a positive integer `timeoutSeconds`. The JSON includes the exit code, timeout flag, duration and last 60 lines of combined output for each check. A completed run exits 0. Configuration and execution errors exit 1 with `{ok:false,error}`. Setup allows the installed CLI path for background sessions.


`branch --issue <n> --name <branch> --from <ref> [--parents <ref,...>] [--remote origin]` requires a clean checkout, fetches remote branch refs and switches to an existing local branch, tracks a remote-only branch or creates a branch from the requested ref. It fast-forwards a local branch that is behind its remote counterpart and refuses divergent history. It reports the chosen branch, action, head, earlier own commits and parent conflicts. Parents merge in the supplied order, and each conflicting merge is aborted before the next one. The engine can pass an explicit matching prefix or require an existing PR branch.

`restore --to <branch>` returns the affected paths when the checkout is dirty and switches to the requested local branch when clean. Branch and Restore require a readable project configuration. Branch creation and merges refuse the configured base and protected branch patterns. Restore can check out a protected branch without writing its ref.

`commit` reads the engine's JSON payload on stdin. It refuses the configured base branch and protected branches. It reports any changed paths outside the supplied QA and dev lists before touching the index. It stages each file by name and creates the QA test commit first, followed by the implementation commit. With separate grouping, repository-root Markdown, `docs/**` and changelog fragments go into a final docs commit. Files under `skills/**` and `agents/**` stay with the implementation. Empty groups are skipped and commit subjects are limited to 100 characters. The runner creates a temporary detached worktree at the QA commit, executes setup and the test command there, and removes the worktree even when setup or the test fails. The JSON includes commit SHAs, subjects and paths, any unlisted paths, whether the test command exited nonzero, and its last 40 output lines.

`push --branch <branch> [--remote origin]` reads the project configuration, refuses the base and protected branch patterns, and requires the named branch to be checked out. It pushes that branch to the same remote branch with upstream tracking and returns `{ok:true,branch,remote,pushed:true}`. The push uses a non-forcing refspec.

`pr-body [--template <path>]` reads the stage results as JSON on stdin and returns `{ok:true,title,body}`. It strips the issue's leading task prefix and limits the conventional title to 72 characters. It fills the template headings in order, removes template comments, renders empty lists as `None`, and omits fix headings on other issues. Without a template it uses the default headings. It appends the three verbatim Review trace lines and run marker, then emits the closing references in payload order.

`lock acquire --name <name> [--wait <seconds>]` takes the named lock by creating a `devflow-<name>.lock` directory under Git's common directory. It retries every 10 seconds for up to 600 seconds by default and replaces locks older than 30 minutes. A busy lock at the deadline returns `acquired: false` with its `heldSince` timestamp. `lock release --name <name>` removes the named lock directory.

## Guard hook (`hooks/guard.py`)

PreToolUse, matcher `Bash|mcp__.*(merge_pull_request|push_files|create_or_update_file|delete_file)`. Exit 2 with a reason on stderr to block:

- any MCP tool whose name ends with `merge_pull_request`;
- MCP tools ending with `push_files`, `create_or_update_file` or `delete_file` when `tool_input.branch` is protected (globs included) or missing/empty (the API then writes to the default branch);
- Bash: `gh pr merge`, `gh api ... /merge` (PUT; an explicit GET is allowed), the GraphQL merge mutations (`mergePullRequest`, `enablePullRequestAutoMerge`), `git push` that targets a protected branch (explicit refspec `:main`, `HEAD:main`, `main`, or pushing while the current branch is protected), `git push --force`/`-f`/`+refspec` (allow `--force-with-lease`), `git push --mirror`/`--all`/`--delete` of a protected branch;
- Bash, git commands that discard work: `reset --hard`, `clean` with `-f`/`--force` in any flag group, `branch -D` (or `-d` with `-f`), `checkout .` / `checkout -- .` (also `./`, `:/`), `restore .` (unless only `--staged`, which just unstages), `stash drop` / `stash clear`, `filter-branch`, `update-ref -d`, `reflog expire`. The message tells Claude to ask the user to run it themselves;
- Bash, skipping hooks: `git commit` with `--no-verify` or `-n` (also in a flag group such as `-nm`; values like `-m "-n"` are not flags) and `git push --no-verify`; `git push -n` is a dry run and stays allowed. `git checkout -f/--force` and `git switch -f/--force/--discard-changes` discard local changes; `git clean` with `-n`/`--dry-run` is a dry run and is allowed even with `-f`;
- Bash, `gh api` writes (explicit non-GET, or `-f`/`-F`/`--field`/`--raw-field`/`--input`) to `git/refs/heads/<protected>` or `.../statuses/<sha>` (forging `devflow/review`); `gh pr edit` / `gh issue edit` removing `labels.riskHigh` (a risk downgrade is a human decision; adding `risk:low` stays allowed because the workflows' gh fallback does it);
- Bash, staging everything: `git add -A`, `--all`, `.`, `./`, `:/`, `*`, `-- .`, combined flags such as `-vA`. `git add -u` stays allowed: it stages only tracked files (how a merge resolution or a rename is staged) and never picks up untracked files. This replaces the per-project `block_git_add_all.py` hook (its cases are in `test_guard.py`).

Global git options before the subcommand (`-C <dir>`, `-c k=v`, `--git-dir=...`, `--no-pager`) are skipped. A wrapper (`sudo`, `env`, `xargs`, ...) is looked through by trying every later `git` / shell token as the start of the wrapped command, so `sudo -u git git add .` is caught without knowing each wrapper's options.

Protected branches = `protectedBranches` + `baseBranch` from `.claude/devflow.json` in the project (`$CLAUDE_PROJECT_DIR`), defaulting to `main`, `master`, `develop` when the file is missing. Parse commands with `shlex` like the TaskBoard `block_git_add_all.py` hook (look through `env`/`sudo`/`bash -c` wrappers; regex fallback when shlex fails). Stdlib only, Python 3.9. Fail closed: any unexpected exception (including unparsable stdin) exits 2 with an "internal error" reason, because any other non-zero exit is a non-blocking error; `/devflow:doctor` check 10 runs the hook to prove it works on the machine. Ship `test_guard.py` (unittest) covering blocked and allowed cases, including that `update_pull_request` and `update_pull_request_branch` stay allowed (`/devflow:sync` needs them). The merge gate Action is outside the hook's reach by design: it is the one place merges happen, and it runs with its own token.

## Formatter and session start hooks

- `hooks/formatter.py`, PostToolUse, matcher `Write|Edit|MultiEdit|NotebookEdit`. Reads `format` (glob to command) from `.claude/devflow.json`; a glob without `/` matches the file name anywhere, one with `/` the path from the project root (`**` crosses directories; no brace expansion). `{file}` is the shell-quoted relative path (appended when absent). Every matching command runs from the project root with a 30 s timeout, output discarded. No config, no key, a file outside the project, a missing binary, a failure or a timeout: exit 0 and nothing printed. It formats; it never decides whether an edit is allowed.
- `hooks/session_start.py`, SessionStart. With a parseable `.claude/devflow.json` it prints `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": <rules>}}` on stdout (stderr would not reach the context): the branch pattern and base, the commit scope with an example, failing test first, stage by name, never edit acceptance criteria or weaken checks, ask on ambiguity, never merge or push to the protected branches, file bugs as `needs-triage`, and the checks. Without one: silent, exit 0.

## Reviewer agent

`agents/reviewer.md` (`devflow:reviewer`, Opus, tools Read/Grep/Glob/Bash, read-only). It carries the review order (correctness, tests, scope, CLAUDE.md, out of scope against the criteria, weakened checks, fix PR fields) and the severity rules. The engine's Review stage passes `agentType: nextTask.reviewerAgent` with its schema; if that type cannot be started it notes it once and uses the default agent for the rest of the run. Users can run it locally on a branch.

## Reusable workflows

`.github/workflows/devflow-review.yml` and `devflow-merge-gate.yml` in this repository run on `workflow_call`. The review's jobs are kept byte-identical to the copy template (`tests/reusable.test.cjs`); the caller holds the trigger, the concurrency group, the permissions and the secrets, passed by name (`CLAUDE_CODE_OAUTH_TOKEN`; `DEVFLOW_GATE_TOKEN` and the optional `DEVFLOW_READ_TOKEN`), because `secrets: inherit` is only guaranteed inside one organization or enterprise and these repositories are user-owned. The gate checks out the caller (for `.claude/devflow.json`) and, sparsely, this repository at the `devflow-ref` input into `.devflow-plugin`, and runs the same gate script, so the logic is not copied into projects. Callers in `skills/init/templates/github/callers/` keep the names the gate needs (`Claude Code Review`) and pin both `uses:` and `devflow-ref` to `{{DEVFLOW_REF}}`. Release tags (`vX.Y.Z`, made by a human) are what callers pin to.
